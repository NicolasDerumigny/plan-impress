# AGENTS.md

Notes for an AI agent working on this repository. Read this before editing: most
of what is here was measured against LibreOffice, not copied from documentation
that turned out to be wrong or incomplete.

## What this is

A LibreOffice Impress extension (`org.devsys.planimpress`) that inserts agenda
slides: one overview slide before the first section, plus one identical plan
slide at the top of each section where only the current section is drawn in the
text colour. A `Plan` menu provides *Insert Plan Slides*, *Remove Plan Slides*,
*Settings…* and *Toggle Debug Log*.

## Layout

```
src/                     the extension package: this tree IS the inside of the .oxt
  Addons.xcu             menu + icons
  description.xml        metadata, version, dependencies
  META-INF/manifest.xml  which files are configuration data / Python components
  handler.py             the com.sun.star.task.Job implementations (menu commands)
  plan_impress/
    core.py              all document-model work (sections, pages, shapes)
    dialog.py            settings dialog + message boxes
    config.py            settings persistence, colour helpers, logging
  icons/                 PNGs generated by dev/make_icons.py
dev/                     harness: run/install/package scripts, debug reproducers
tests/run_tests.py       the test suite (plain Python, no framework)
tests/make_fixture.py    creates the two fixture decks (see its docstring)
Makefile                 make | install | start | stop | test | unit | icons | fixture | clean
```

`out/` and `loprofile/` are generated and git-ignored. Never commit them.

## Commands

```sh
make test       # install + full suite against the dev office (needs X; start_ui.sh starts Xvfb)
make unit       # the tests that need no office (colour helpers, dialog layout)
make install    # stop office, package src/, unopkg add, start office
python3 tests/run_tests.py <substring>     # run a subset of the tests
python3 dev/open_fixture.py   # open the fixture in the dev office, for a UI check
python3 dev/render_plan.py    # insert with the *saved* settings, export PDF + PNGs
dev/run_one_test.sh <substring>   # one test on a fresh office: says if soffice survived
python3 dev/debug_two_documents.py  # two decks, one shared settings file (fact 58)
python3 dev/debug_rollback.py --case moves|build|check   # a run that stops half way
```

`make test`/`make install` need `DISPLAY` pointing at a live X server (the dev
setup is in fact 37). `dev/` scripts that read settings from outside the office
need `PLAN_IMPRESS_DATA_DIR` (fact 33).

The dev office is a **separate** LibreOffice with its own profile
(`loprofile/`) and its own UNO socket (port 2009). Do not kill the user's own
soffice; `dev/stop_lo.sh` matches only the dev instance by its profile path, and
`unopkg` must run while the dev soffice is **stopped** (it prints
`ERROR: unopkg failed.` otherwise). Extension code is cached inside the office
process, so a change only takes effect after `make install` (which restarts it).

## Conventions

* Python 3, no dependencies beyond what LibreOffice ships. Keep the code
  compatible with the Python embedded in LibreOffice 7.x (3.8+), i.e. no
  walrus-dependent cleverness, no 3.10-only syntax.
* `core.py` contains only document-model code and never imports `dialog.py`;
  that separation is what lets the tests drive `core` directly.
* Errors the user should see are raised as `core.PlanError` with a message that
  says what to do next; anything else is logged to `error.log` and reported.
* Keep the "why" comments. The unusual lines in this codebase exist because of a
  specific measured LibreOffice behaviour, and a well-meaning cleanup that
  removes one of them reintroduces a real bug.

## LibreOffice facts this code depends on

All of these were verified on LibreOffice 26.8.2.2 on Linux. Each one is
reproducible with a script in `dev/`.

### Packaging

1. **`description.xml` dependency spelling.** Use
   `<lo:LibreOffice-minimal-version value="7.0" d:name="LibreOffice 7.0"/>` in
   the namespace `http://libreoffice.org/extensions/description/2011`. An element
   with the *same name* in the 2006 namespace fails with
   `unsatisfied dependencies` whatever value it carries, and
   `OpenOffice.org-minimal-version` is compared against
   `ReferenceOOoMajorMinor` (`4.1` in `program/versionrc`), so asking for `"7.0"`
   there fails as well. `dev/dep_probe.py` walks through every spelling.
2. **Only register what must be registered.** `META-INF/manifest.xml` declares
   `Addons.xcu` (`configuration-data`) and `handler.py`
   (`uno-component;type=Python`). The `plan_impress` package is *not* declared:
   `handler.py` adds its own folder to `sys.path` and imports it normally.
3. **No `com.sun.star.*` imports at module level** in anything the extension
   manager loads. During registration those imports fail
   (`ImportError: No module named 'com'`) and registration is skipped with only
   a warning on stderr — the extension then looks installed but has no menu and
   no error message. Import them inside functions/methods. `handler.py`
   additionally guards `from com.sun.star.task import XJobExecutor` at module
   level and falls back to `object`, because the class definitions must be
   evaluable at registration time.
4. `unopkg` does not replace a running installation: stop the office first, and
   `unopkg remove <identifier>` before `add` when testing packaging changes.

### Menu (`Addons.xcu`)

5. Top-level menus are added with `OfficeMenuBarMerging`. `MergePoint` is a
   **menu path of item commands** separated by backslashes — `.uno:SlideShowMenu`
   puts us after *Slide Show*. `MergeCommand` accepts
   `AddAfter | AddBefore | Replace | Remove`; `MergeFallback` accepts
   `AddPath | Ignore` (`AddLast` is a *toolbar* token and is silently ignored
   here).
6. `MergeContext` and each item's `Context` are matched against the module
   identifier `ModuleManager::identify()` returns for the document model — for
   Impress that is `com.sun.star.presentation.PresentationDocument`. A wrong
   value fails **silently**: the menu just never appears.
7. A submenu node needs `Title` + a `Submenu` child and must **not** carry a
   `URL`; the leaf items need `URL` + `Title` + `Target=_self`.
8. Icons go under `AddonUI/Images`, keyed by the same `URL` as the menu item,
   with `%origin%/icons/…` paths (`%origin%` = the extension's own folder).
9. The configuration is only re-read at startup; after changing `Addons.xcu`
   you must restart the office (`make install` does it).

### Calling into Python

10. Menu items use `service:<implementationName>?<args>` bound to
    `com.sun.star.task.Job`, registered with `unohelper.ImplementationHelper()`
    in `handler.py`. LibreOffice then calls `XJobExecutor.trigger(args)`. This
    is the SDK's own pattern; `vnd.sun.star.script:` URLs are fragile because
    they embed the installed `.oxt` file name and
    `location=user:uno_packages`.
11. **Run the work inline in `trigger()`.** Executing the same document work
    from a Python **worker thread crashes the office** (`free(): invalid
    pointer`, `Unspecified Application Error`, whole process gone). The
    `.uno:MovePageUp/Down` commands are nevertheless asynchronous, so
    `core.insert_page_at()` polls for the index change instead of hoping.
    `PLAN_IMPRESS_DEFER=1` switches to a `com.sun.star.awt.Timer` main-loop
    deferral; keep that path working — it is the debugging tool for dispatch
    ordering.

### The document model

12. **Sections.** `doc.SlideSections` is a
    `sequence<com.sun.star.beans.PropertyValue>` whose values are themselves
    property-value sequences (`Name`, `Id`, `SlideNameList`). Writing it back
    only works when the nested values carry an explicit `uno.Any` type:
    `uno.Any("[]string", tuple(names))` and
    `uno.Any("[]com.sun.star.beans.PropertyValue", inner)`. Plain tuples are
    **silently dropped** — the assignment appears to succeed and nothing
    changes. Empty sections are kept by LibreOffice and are ignored here.
    What the list *means* is the trap: the document stores a **contiguous range
    of positions** and renders it back as names, and the name a page answers to
    is its `LinkDisplayName` (`"Slide 3"`) or the value a client last assigned to
    `page.Name` — **never** the `DrawPages` name (`page3`). So a deck the user
    made in Impress lists its sections as `Slide 3`, `Slide 4`, …, matching
    nothing in `DrawPages`, and comparing the two made *Insert Plan Slides*
    refuse to work on any real document. On a write, each name is resolved to
    the position it names *now*, unmatched names are dropped in silence, the
    ranges stretch over the gaps and the **last section always runs to the end
    of the deck** ("these slides belong to no section" cannot be expressed). All
    of it is printed by `dev/debug_sections.py`; `core.get_sections()` resolves
    names to indexes and `core.set_sections()` takes indexes back.
13. **`XDrawPages.insertNewByIndex(k)` inserts *after* position `k`**, clamps
    `k` to the page count, and can therefore never reach index 0. The container
    has no reorder method. `core.insert_page_at()` compensates: insert, then
    walk the page into place with `.uno:MovePageUp` / `.uno:MovePageDown`.
14. Those move commands act on the slide the **view** has selected, so
    `controller.setCurrentPage(page)` first. `controller.select(page)` does
    **not** work (measured: the page never moves — `dev/debug_move.py`). They
    are also asynchronous, hence the polling in `_wait_for_move`.
15. Insertions do **not** shift section membership: sections must be rewritten
    after every insertion (that is why `insert_plan` recomputes the whole list
    at the end and inserts bottom-up so the pending targets stay valid). Nothing
    identifies a page across such a change either — LibreOffice renumbers the
    automatic `pageN` names by position, so the slide that was `page3` is
    `page4` afterwards (`dev/debug_sections.py` prints it) — hence
    `core._section_with_plan()` computes where the slides *must* have ended up
    and `_check_sections()` reads the list back and refuses to pretend success.
    The assignment drops the section `Id` unless it is sent back, so
    `set_sections()` carries it through.
16. **Deleting a slide that anchors a section corrupts the section list**
    (measured: three sections became two with the wrong slides in them). So
    `remove_plan_slides()` snapshots the cleaned section lists first and
    rewrites them after the deletions. Do not "simplify" that.
17. **Only slides before the first section may be ungrouped.** Writing
    `doc.SlideSections` normalises the lists: a slide that belongs to no section
    and sits *after* the start of the first section is appended to the section in
    front of it (measured with `dev/debug_ungrouped.py`: sections `A=[s1,s2]`,
    `B=[s4]` over six slides came back as `A=[s1,s2,s3]`, `B=[s4,s5]`). Slides
    before the first section do survive, which is what lets a title slide stay
    outside every section while `insert_plan` puts the overview at the first
    section's start.
18. `com.sun.star.presentation.SubtitleTextShape` raises
    `ServiceNotRegisteredException`; `com.sun.star.presentation.OutlinerShape`
    and `com.sun.star.drawing.TextShape` work. `core.BODY_SERVICES` tries them
    in that order.
19. Never test a shape type with `"Title" in shape.ShapeType` — the body
    placeholder's type is `...SubtitleTextShape`, which also contains "Title".
    Use `supportsService("com.sun.star.presentation.TitleTextShape")`
    (`core._is_title`).
20. **`CharHeight` is a point size; every geometry property is 1/100 mm.** Never
    derive one from the other: the original `height / 100` formula produced a
    262 pt heading (`dev/debug_sizes.py` prints the shape, paragraph and portion
    values). `core._master_char_height()` takes the size from the master
    placeholder (44 pt title / 32 pt body in the default master) and falls back
    to `_TITLE_PT`/`_BODY_PT`; `_fit_point_size()` shrinks the list so all
    sections still fit under the heading, and `_UNITS_PER_POINT` (35.28, not
    3528) is the only place the conversion happens.
21. **Do not copy a master placeholder's rectangle blindly.** The default
    Impress master keeps its title placeholder at `y = -32 mm` about two thirds
    of the page tall; used verbatim the heading is drawn outside the slide.
    `core._rect()` takes the rectangle only when it fits on the page and
    otherwise uses the computed fallback. Impress also re-snaps a presentation
    placeholder to the master and auto-grows it, so the rectangle you set is not
    always the one you read back — check the rendered result, not the property.
22. Presentation placeholders **anchor their text in the middle of the box**, so
    a one-line heading floats down into the body; `_make_text_shape` sets
    `TextAnchor` (awt `TOP` = 0) and `TextAnchorKind` (drawing `TOP` = 1) — but
    only when `TextVerticalAdjust` could not be mirrored from the master: with it
    mirrored, the master's own anchoring is the template's and has to survive.
23. Per-paragraph colour is set on the paragraphs of `createEnumeration()`
    (`_paint_paragraphs`), and a plain-text shape created with `setString()`
    treats `\n` as a paragraph break.

### AWT (`dialog.py`)

24. `dialog.Model = model` **raises** (`UnknownPropertyException: ... property
    is readonly`) — use `dialog.setModel(model)`.
25. **Control models must come from the dialog model's own `createInstance()`.**
    That is what `/usr/lib/libreoffice/program/wizards/ui/UnoDialog.py` does, and it
    is the whole reason the form has a layout: such a model keeps
    `PositionX`/`PositionY`/`Width`/`Height`, while one from the service manager has
    *no* geometry properties at all, so every control lands at 0,0 with its natural
    size and the settings dialog is an unreadable pile in the corner.
    `dev/debug_dialog_props.py` prints the two property sets side by side.
26. `XNameContainer.insertByName()` on a dialog model **rejects** the documented
    `sequence<PropertyValue>` carrying a `Servicename` (`IllegalArgumentException`
    in every spelling tried — control or model service name, list/tuple/`uno.Any`,
    with or without geometry, before or after the peer exists:
    `dev/debug_dialog_insert.py`). Insert the model object instead.
27. The dialog's **window size is a model property**: set `Width`/`Height` on the
    dialog model (`Width=140` → a 354-wide window, `dev/debug_dialog_windowsize.py`).
    `XControl::setPosSize` moves the dialog and silently **discards the size**, so
    `setPosSize(..., POS | SIZE)` still leaves the 300x450 default; use it for the
    position only, as `dialog._centre()` does.
28. Those coordinates are **AWT dialog units** — neither pixels nor 1/100 mm. One
    unit is about 2.5 px of peer geometry (measured 2.53 x 2.39 in
    `dev/debug_dialog_units.py`), which puts the form at 176x145 units ≈ 445x367 px —
    the same magnitude as the wizards, which give a label `Height=8`.
29. The two factories have different property sets: the container's own adds
    `PositionX/Y`, `Width`, `Height`, `Name`, `Tag`, `Step`, `TabIndex`,
    `ResourceResolver` and **lacks** `MaxLen`, `TabStop`, `TabPosition`, `Multiple`.
    Those four are therefore not set: the hex fields are validated in `result()`
    and the tab order follows position. `setPropertyValues()` fails *as a whole* if
    one property is unknown, which is why `_apply()` falls back to one by one.
30. A list box only shows a selection when `SelectedItems` travels **with the model
    into `insertByName`**; set on the inserted child it is accepted and then ignored
    by the peer (`getSelectedItemPos()` stays -1 — `dev/debug_dialog_masters.py`).
    Sequence properties need explicit typing: `uno.Any("[]string", ...)` for
    `StringItemList`, `uno.Any("[]short", ...)` for `SelectedItems` (0-based).
    `getControl(name)` exposes a limited method set: `selectItem()`/`selectItemPos()`
    raise on the argument count and there is no `getPropertyValue`.
31. Give every button its **own** `XActionListener`. Deciding which one was pressed
    from `event.Source.Model.Name` failed silently, so OK became a cancel: the
    dialog closed and nothing was saved.
32. `Toolkit.createMessageBox(parent, type, buttons, text)` builds the message
    boxes, with `MessageBoxType` `0|3|4` (message/warning/error) and
    `MessageBoxButtons` `1` (OK) or `5` (Yes/No); `execute()` returns
    `MessageBoxResults` (`6` = Yes). Always `dispose()` in a `finally`, and never
    let a reporting failure swallow the real error. `setTitle()` works on the
    dialog, `setPropertyValue("Title", …)` does not.

### Settings and logs (`config.py`)

33. **The profile comes from the deployment path, not from the office.** Asking
    pyuno is a dead end — `PathSettings.User` and
    `PathSubstitution.getSubstitutedValue()` both raise `AttributeError` there —
    and the old hard-coded `~/.config/libreoffice/4/user` fallback made the
    extension save into a *different* LibreOffice, so pressing OK appeared to do
    nothing. A deployed extension lives under `<profile>/user/uno_packages/...`, so
    `config._profile_from_path(__file__)` reads the profile out of its own path.
    `PLAN_IMPRESS_DATA_DIR` overrides it, which the `dev/` scripts need because
    they run outside the office and have no deployment path.

### Out-of-process test scripts

34. A remote document proxy does **not** expose `getComponentContext()`, so
    `core`'s functions take an optional `ctx` argument (`insert_plan(doc,
    settings, ctx)`). Keep it optional — the in-process Job relies on the
    default — and pass the connected context from tests.
35. Tests need a controller and a frame (moving slides and dispatching commands
    both require one), so they load documents **non-hidden** against the UI-mode
    dev office. `lo.open_doc(..., hidden=False)` waits for the controller.
36. The office logs to `out/soffice.log`. The extension's own logs are
    `loprofile/user/planimpress/error.log` (always written) and `debug.log`
    (only with the `debug` marker file in that folder, or
    `PLAN_IMPRESS_DEBUG=1`); the *Toggle Debug Log* menu item flips it.
37. The UI itself can only be checked on a real display:
    `Xvfb :98 -screen 0 1440x900x24` plus `marco --replace` as window manager,
    `DISPLAY=:98 make install`, `python3 dev/open_fixture.py`, then drive the menu
    with `xdotool mousemove X Y click 1` and capture with `scrot -o`.
    `dev/render_plan.py` renders the generated slides to PDF/PNG instead, and
    `dev/show_plan.py` inserts the slides and puts one in front of the controller
    for the screenshot. Both are how the settings dialog was finally confirmed —
    assertions had passed the whole time it was unusable.

### The footer band (`core.apply_footer`)

38. **The footer belongs to the slide, not to the document.** `FooterText`,
    `DateTimeText`, `DateTimeFormat`, `IsDateTimeFixed`, `IsFooterVisible`,
    `IsDateTimeVisible` and `IsPageNumberVisible` are properties of the *page*
    (`com.sun.star.presentation.DrawPage`; they are the ODF
    `presentation:display-*` flags and `draw:footer-text`). On the document they
    raise `AttributeError`, and so do `page.StyleName` and
    `doc.StyleFamilies["PageStyles"]` — `dev/debug_footer_switches.py` prints
    where they really are. A page from `insertNewByIndex` has all of them empty,
    which is what made the generated slides footer-less.
39. **Switched on is not the same as printing.** A fresh deck reports
    `IsFooterVisible=True`, `IsDateTimeVisible=True`, `IsDateTimeFixed=True` with
    both texts empty, and prints nothing; `fixtures/sections_no_footer.odp` is
    that deck, and `core._footer_prints()` is what keeps a footer from being
    invented there. A date that is a field (`IsDateTimeFixed=False`) does print —
    today's date.
40. **Copying those properties is enough for a deck authored in Impress**, because
    the master page's own placeholders do the drawing — and a `FooterShape`
    created empty on the page neither draws nor hides anything
    (`dev/debug_footer_render.py` exports the variants next to each other). A deck
    written elsewhere keeps a real frame per slide instead
    (`presentation:class="footer"` in `content.xml`); those are recreated by
    `_mirror_footer_shapes`, with the master's rectangle and character height.
41. **The date and the page number are text *fields*, not characters.** Copy them
    by inserting the field object — `text.insertTextContent(cursor,
    portion.getPropertyValue("TextField"), False)` — and it prints the number of
    the slide it now sits on, so every plan slide gets its own. `getString()` of a
    field portion answers with the placeholder stored in the file (`<footer>`,
    `<number>`) or with whatever the last layout pass painted: never assert on it,
    render instead. `core.FOOTER_FIELD_SERVICES` recreates a field from its service
    when the object cannot be reached.
42. All four band shapes — `com.sun.star.presentation.HeaderShape`,
    `DateTimeShape`, `FooterShape`, `SlideNumberShape` — *are* creatable, unlike
    `SubtitleTextShape` (fact 18), and neither `XShapes.add()` of an existing shape
    nor `createClone()` copies one between pages, so they have to be built
    (`dev/debug_footer.py`). A freshly created one already holds its own field, so
    clear the shape before putting anything into it.
43. `core.footer_source()` picks the first non-generated slide whose band prints
    something, or `None`; `insert_plan` looks it up once and passes the same slide
    to every `build_plan_slide`, so all plan slides agree with each other.

### The settings dialog's own look (`dialog.py`)

44. **The dialog sets its own text size.** Control models take `FontHeight` in
    points, and at the original 10 the labels measured 13 px of ink where a Plan
    menu item measures 14 px — the report was "text on the setting pane is smaller
    than the menu text". `dialog._FONT` is 12, which measures 17 px (12 px of caps
    plus the mnemonic underline): the same face the menus use. `dev/measure_text.py`
    screenshots the dialog and the open menu and prints both heights, because no
    property assertion can see this.
45. Rows are spaced by `_ROW_STEP = _FIELD_H + _ROW_GAP`, i.e. a row is its field
    plus clear air under it. Spacing each row by a fixed 14 units for 12-unit fields
    left the next label 2 units under the previous field, which is what "the entries
    are too cramped" meant. Both are asserted in
    `tests/run_tests.py dialog_text_is_readable_and_rows_are_not_cramped`.
46. Nothing on a control peer tells you what font it renders: `FontDescriptor`,
    `FontName` and `FontHeight` are all absent from the peer proxy
    (`dev/debug_font.py` prints `<none>` for every one). Judge text size from
    pixels — `dev/measure_text.py` counts the bright rows of a screenshot (this
    theme is dark, so text is the *light* pixels: thresholding for dark pixels
    measures the background and reports every row as text).

### Verifying a change (both agents hit both of these)

47. When you check that a test fails without the fix by editing `src/` and putting it
    back: if the edit and the restore land in the same second and the file ends up the
    same size, the `.pyc` keeps the mutated bytecode and the "restored" run still
    fails. Remove `__pycache__` (or `make clean`) before trusting such a run.
48. `dev/stop_lo.sh` kills soffice, so a document of the run just killed keeps its
    `.~lock.<name>#` file. The next `loadComponentFromURL()` then waits on a modal
    "the document is in use" dialog and the script hangs without printing anything;
    the dialog also survives the client and wedges every later load until the office
    is restarted. `dev/lo.py:clear_lock()` removes it before loading, and a hang in
    `open_doc` means restarting the office, not the script.

### The template's own look (`core.py`)

A generated slide has to look like the deck's own slides were *edited*. Everything
below was measured with `dev/debug_numbering.py` (one PDF, a slide per variant) and
`dev/debug_style_source.py` (what the masters, the deck's own slides and the
generated ones say about themselves, side by side) on LibreOffice 26.8.

49. **Inherit the master's list level and write only `NumberingType`.** Copy all
    ten levels of the master content placeholder's `NumberingRules` and patch the
    first one: a rules object built from scratch gives the digits a font, a size, a
    gap and a colour of their own, and they look pasted onto the slide.
    `NumberingType` has to be the **integer** of `NumberingType.ARABIC` (`4`) — `1`
    is `CHARS_LOWER_LETTER`, which is the "a. b. c." the first attempt rendered, and
    a value pyuno marshals from a string arrives as 0, i.e. no label at all — and
    the level goes back as `uno.Any("[]com.sun.star.beans.PropertyValue",
    tuple(level))`. `Prefix` and `Suffix` are literal text: `"%1."` prints `%1.`.
50. **The properties that describe the glyph have to be re-asked for.**
    `BulletRelSize` sizes the *character* the template draws — the fixture's master
    asks for 45 % of the text height, which is an unreadable digit — so when the
    label is a special character (`NumberingType` 6 or 8) it becomes
    `max(inherited, 100)`. The label's column likewise: two slides whose level read
    exactly the same (`LeftMargin` 1200, `FirstLineOffset` -1200) rendered with and
    without a gap, and what separated them was the **paragraph's**
    `ParaLeftMargin`/`ParaFirstLineIndent`, so those are set from the level's indent
    or the digit sits on the text (`1Introduction`). `SymbolTextDistance` is no
    help: writes to it are ignored and it mirrors `FirstLineOffset`.
51. **Dim a row's number with a rules object of its own.** The label is painted with
    the level's `BulletColor`, so one copy of the rules per paragraph differing in
    that one property dims the sections that are not the current one — and the list
    still counts 1, 2, 3 across the different rule objects. The `Bullet*` properties
    of a *paragraph* are refused outright (`BulletColor`, `BulletChar`,
    `BulletNumberingType`, `BulletRelSize` all raise), which is why the rules have to
    be copied. A template that fixes no bullet colour (`-1` = follow the text) gets
    the highlight colour on the current row.
52. **Mirror the template placeholder's characters onto the shape *and* onto its
    paragraphs, from its first paragraph.** A shape from `createInstance()` comes in
    the page style's font, and a *paragraph* of an outline placeholder comes in the
    page style's outline level — `CharWeight` 150 where the template's own
    placeholder says 100, so the list rendered bold next to the deck's own slides.
    The source is the template placeholder's **first paragraph** (`_first_paragraph`)
    when it has one and its shape otherwise: on a real master the two disagree, and
    the paragraph is the outline level the deck is drawn with.
    `core.CHAR_ATTRIBUTES` is the shape's list, `core.PARAGRAPH_ATTRIBUTES` the
    paragraph's (no `CharStyleName`, which a paragraph does not have; no
    `CharHeight`/`CharColor`, which are ours).
53. **Setting `page.Layout` creates the placeholders.** `page.Layout = 2` on a fresh
    page hands back a `TitleTextShape` and an `OutlinerShape` of its own, so adding
    shapes without looking for them yields four; `_ensure_placeholder()` reuses what
    is there. No dispatch route does it better: `.uno:AssignLayout?Layout:short=2`,
    `.uno:AppendPage` and `.uno:InsertPage` are measured no-ops. The layout is
    therefore the *first* thing `build_plan_slide` does after clearing the page, and
    `apply_footer()` runs right after it: assigning a layout re-deals the
    placeholders, so a footer frame mirrored onto the page before it is at the mercy
    of that step.
54. **The deck's own slides are the template; the master page is the fallback.**
    `_style_source()` asks the slides first (`_deck_placeholder`) and the master
    only where no slide has anything to copy, because a slide keeps the box and the
    characters it was given and the two disagree on any deck somebody worked on —
    measured on a deck off the disk, whose master placeholder says `1800,1500`
    `24400x1040` at **32 pt** while its six content slides are all at `1800,1474`
    `24400x1094` at **31 pt**: taking the master produced a heading a point larger
    than the deck's own, a few tenths of a millimetre away from it. The value the
    slides *agree on* wins (they are counted per rectangle-and-look), which is what
    keeps one hand-edited slide, or the cover slide that is usually first, from
    moving the generated ones; `dev/debug_style_source.py` prints the three sets
    side by side.
55. **A presentation placeholder's characters live on its paragraphs.** A master's
    content placeholder keeps **one paragraph per outline level**, so its first
    paragraph is level 1 and is what the slides paint with; the shape's own
    `CharHeight` is only the default underneath it (`32` against the paragraph's
    `31`, `20`/regular against `21`/semibold on the deck above). Ask the paragraph
    first (`_master_char_height`, `_first_paragraph`) — on the shape's value the list
    came out smaller and lighter than the deck's own body text.
56. **The heading has to be measured where it *paints*, not by its box.**
    Presentation placeholders anchor their text in the middle of the box, so a
    template box twice as tall as its one line leaves the text in the middle of the
    box; the list only has to clear *that*. `_heading_bottom()` takes the anchor
    (`_text_anchor`, read back from the shape after mirroring) and returns the bottom
    of the painted line — box top + line for `TOP`, box top + (box + line)/2 for
    `CENTER`, box bottom for `BOTTOM`. Comparing against the box's top let the list
    overlap the heading on the fixture (its title box spans 1575..4725 while its
    body box starts at 3685).
57. **The deck's numbering format lives with the heading, not with the body.** The
    first `NumberingType` that is worth copying is the content level's own; where that
    level draws a glyph instead of counting, the deck is asked in the order deck
    content, deck **title**, master content, master title (`_label_sources`) — a
    template keeps its numerals in the heading and its decoration in the body, and on
    the deck this was measured on the content level is `CHAR_SPECIAL` with an OpenSymbol
    arrow while the title level counts `ROMAN_UPPER` with a `.` suffix
    (`style:num-format="I"` in `content.xml`). Taking the label from another level
    takes its `Prefix` and `Suffix` with it — the text around the number is the format
    as much as the numerals are — but *not* its `LeftMargin`, `FirstLineOffset` or
    `BulletRelSize`, which belong to a heading. The measured `NumberingType` values are
    `CHARS_UPPER_LETTER 0, CHARS_LOWER_LETTER 1, ROMAN_UPPER 2, ROMAN_LOWER 3, ARABIC 4,
    NUMBER_NONE 5, CHAR_SPECIAL 6, PAGE_DESCRIPTOR 7, BITMAP 8`; nothing in
    `(6, 8, 0, 5, 7)` counts (`_uncounted_labels`), so only those get digits. The size
    and column correction of fact 50 belongs to *that* case alone: when the label is the
    template's own, whatever it asks for stays.

### Working on two documents in one office (`insert_plan`)

58. **The settings are per profile, so the master they name is usually another
    deck's.** A `master` that this document has no master page for is *not* an error —
    it means "the deck's own", exactly like the empty setting (`_master_page` falls back
    to `_default_master`). Refusing there is the report "inserting plan slides does
    nothing in the second deck until I open *Settings*": the office logs it as
    `Master slide 'Blue_Curve1' no longer exists`, and *Settings* appeared to fix it
    because its master list is filled from the deck in front, so saving there wrote a
    name that deck has. `insert_plan` reports which master it used and whether the
    settings named one this deck has (`master`, `master_named`). `_default_master()`
    counts the masters of the deck's *own* slides and ignores generated ones, or the
    second run picks what the first one's slides used instead of what the deck uses.
59. **`insert_plan` is all-or-nothing.** Everything that can refuse is settled before
    the deck is touched — the master above all, which used to be resolved once *per
    generated slide*, i.e. after pages had been inserted — and any later failure goes
    through `_drop_pages()`: every generated slide out (all of them, not just the ones
    that were reported inserted: `insert_page_at` raises *after* `insertNewByIndex`) and
    the section list written back the snapshot taken after the initial
    `remove_plan_slides()`. A deck left half-inserted has empty slides in it and sections
    that no longer match its slides, and the next run then cleans a wreck instead of a
    deck — measured as three sections coming back as one (`dev/debug_two_documents.py`,
    `dev/debug_rollback.py`). It is *not* the move commands losing the second deck's
    page: `dev/debug_move_race.py` inserts and removes the plan slides over six rounds
    with another deck open and loses nothing, worst case one dispatch round.
    `remove_plan_slides()` does **nothing at all** when there is nothing to delete,
    because writing `SlideSections` normalises the deck (fact 17) and a run that was
    only looking for old slides must not move a boundary.

### The dev office under a long test run

60. **A long UI session takes the office down, and it is not the extension.** Once a
    few dozen documents have been loaded, moved and closed, soffice dies of
    `free(): invalid pointer` / `Fatal exception: Signal 11`, the stack going from
    `libbinaryurplo` through `cppu::OWeakAggObject::release` into `libeditenglo` — pyuno
    letting go of a text object whose document is already gone. It is LibreOffice under
    load, not this code: running the *committed* suite a second time in the same office
    process does it too, on documents the extension never sees. Where the death lands is
    a matter of luck, and everything after it fails with `cannot connect to soffice`, so
    `tests/run_tests.py` notices the office has gone (`lo.is_alive()`, `lo.died()` — the
    socket stays open for a moment after the process starts to die, which is why both the
    `/proc` command line and the port are checked), starts a new one and gives that test
    its one retry; a test that fails twice has failed. Nothing is hidden: the run ends
    with `office restarted N time(s)`.
61. **A load right after a start answers with a *null* document.** The office answers
    its UNO socket before the desktop can create a document, and
    `loadComponentFromURL()` then returns a null proxy instead of raising; the caller's
    first property read is the unhelpful `cannot get value DrawPages`. `lo._load()` waits
    for the proxy to answer `getURL()` before handing it over.

## Testing notes

`tests/run_tests.py` has no framework: `@test` collects functions, a `Skip`
exception reports "not installed" without failing, and an argument filters by
substring (`python3 tests/run_tests.py dialog`). Tests that need the installed
extension are skipped when it is not installed, so `make unit` is useful without
packaging.

The suite covers: settings round-trip and corrupt-file tolerance, where the
settings file is allowed to live, colour helpers, the point/unit conversion, the
dialog's *geometry* (every control's rectangle in the specs, and the real peer
geometry: distinct positions, non-zero sizes, nothing outside the window) plus a
control model with a native peer and read-back values and the dialog's **text**
(every control that shows words sets a `FontHeight` the size of the menu's, and
each row leaves clear air under the field above it), the inserted layout
(position of every plan slide, per-paragraph colours, the overview outside all
sections), a deck whose first slide belongs to no section, readable font sizes
with nothing drawn off the slide, the footer (copied from the deck's own slides
and rendered, frames mirrored onto a deck that carries them, and no footer
invented in a deck that has none), the template's own look
(`plan_slides_use_the_template_placeholders`: the deck's own placeholders and
their rectangles, the list clearing the painted heading, the inherited list level
with only the label replaced, the characters mirrored down to the paragraphs, the
number of a dimmed row dimmed with it; and `plan_slides_copy_the_deck_own_slides`,
where the master is left alone and the slides moved instead, so anything taken
from the master shows up as a failure), the label the rows are numbered with
(`plan_rows_are_numbered_the_way_the_template_numbers`: the deck's own counting
level with its `Suffix`, its size and its column kept; digits only where nothing
counts, then corrected to be readable; and the numerals taken from the *heading's*
level when the body draws a glyph — `list_label_follows_the_template` pins the
same rule without an office), that a named master the deck does not have means the
deck's own (`master_slide_is_used`), that a run which stops half way leaves neither
a slide nor a section boundary behind
(`insert_plan_leaves_nothing_behind_when_it_fails`, at the three places it can
stop), that removing the slides of such a wreck loses nothing of the deck,
idempotency and clean removal, the master-slide setting, `Addons.xcu` registration
read back through the configuration provider, and the `service:` URL dispatch path a
menu click takes.

Things that are easy to break and are covered: re-running `insert_plan` must
yield the identical slide list (this is what caught the section-corruption bug),
and `remove_plan` must return to the original seven slides and be harmless when
there is nothing to remove. `insert_plan_with_default_slide_names` covers the
shape a deck the user made in Impress has — `page1`, `page2` in `DrawPages` but
`Slide 1`, `Slide 2` in the section list — because the fixture renames every
page and therefore hides that spelling; it builds its own deck, saves it, reads
it back and asserts the section ranges (`indexes`), their `Id`s and that the
trailing unsectioned slide ends up in the last section.

### Looking at the result

Assertions cannot tell you a slide looks right, and a font size that is wrong by
a factor of ten passed every test once. To see the generated deck: export a
document with the plan slides inserted to PDF
(`storeToURL(..., FilterName=impress_pdf_Export)`) and rasterise it with
`pdftoppm`/`montage`, then look at the images. `dev/debug_sizes.py` prints the
`CharHeight` at shape/paragraph/portion level plus the rectangles, which is
usually the faster way to spot a layout problem.

For anything the *text* of a slide has to prove — the footer above all — the PDF
is the only witness: `pdftotext -f N -l N deck.pdf -` per page is what
`tests/run_tests.py::_pdf_page_texts` and `dev/debug_footer_saved.py` assert on,
because `getString()` of a field reports the stored placeholder rather than what
is drawn (fact 41). `dev/debug_footer_render.py` exports several candidate recipes
as one document so they can be compared as images, which is how the footer
mechanism was picked.

## If something is broken

1. Is the extension registered?
   `unopkg -env:UserInstallation=file://$PWD/loprofile list` — look for
   `is registered: yes` under each bundled package.
2. Does the office still have the old code? Restart (`make install`).
3. Read `loprofile/user/planimpress/error.log` and `out/soffice.log`.
4. Turn on the debug log and reproduce.
5. Reproduce in isolation with one of the `dev/debug_*.py` / `dev/dep_probe.py`
   scripts before changing `src/` — every surprising behaviour in this project
   was nailed down that way, and the answer usually is one of the numbered facts
   above.
