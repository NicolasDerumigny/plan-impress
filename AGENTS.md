# AGENTS.md

Notes for an AI agent working on this repository. Read this before editing: most
of what is here was measured against LibreOffice, not copied from documentation
that turned out to be wrong or incomplete.

## What this is

A LibreOffice Impress extension (`org.devsys.planimpress`) that inserts agenda
slides: one overview slide before the first section, plus one identical plan
slide at the top of each section where only the current section is drawn in the
text colour. A `Plan` menu provides *Insert Plan Slides*, *Remove Plan Slides*,
*Insert Section Titles*, *Remove Section Titles*, *Settings…* and *Toggle Debug Log*.

## Layout

```
src/                     the extension package: this tree IS the inside of the .oxt
  Addons.xcu             menu + icons
  description.xml        metadata, version, dependencies
  META-INF/manifest.xml  which files are configuration data / Python components
  handler.py             the com.sun.star.task.Job implementations (menu commands)
  plan_impress/
    core.py              all document-model work (sections, pages, shapes)
    dialog.py            settings dialog + message boxes
    config.py            settings persistence, colour helpers, logging
  icons/                 PNGs generated by dev/make_icons.py
dev/                     harness: run/install/package scripts, debug reproducers
tests/run_tests.py       the test suite (plain Python, no framework)
tests/make_fixture.py    creates the two fixture decks (see its docstring)
Makefile                 make | install | start | stop | test | unit | icons | fixture | clean
```

`out/` and `loprofile/` are generated and git-ignored. Never commit them.

## Commands

```sh
make test       # install + full suite against the dev office (needs X; start_ui.sh starts Xvfb)
make unit       # the tests that need no office (colour helpers, dialog layout)
make install    # stop office, package src/, unopkg add, start office
python3 tests/run_tests.py <substring>     # run a subset of the tests
python3 dev/open_fixture.py   # open the fixture in the dev office, for a UI check
python3 dev/render_plan.py    # insert with the *saved* settings, export PDF + PNGs
dev/run_one_test.sh <substring>   # one test on a fresh office: says if soffice survived
python3 dev/debug_two_documents.py  # two decks, one shared settings file (fact 58)
python3 dev/debug_rollback.py --case moves|build|check   # a run that stops half way
```

`make test`/`make install` need `DISPLAY` pointing at a live X server (the dev
setup is in fact 37). `dev/` scripts that read settings from outside the office
need `PLAN_IMPRESS_DATA_DIR` (fact 33).

The dev office is a **separate** LibreOffice with its own profile
(`loprofile/`) and its own UNO socket (port 2009). Do not kill the user's own
soffice; `dev/stop_lo.sh` matches only the dev instance by its profile path, and
`unopkg` must run while the dev soffice is **stopped** (it prints
`ERROR: unopkg failed.` otherwise). Extension code is cached inside the office
process, so a change only takes effect after `make install` (which restarts it).

## Conventions

* Python 3, no dependencies beyond what LibreOffice ships. Keep the code
  compatible with the Python embedded in LibreOffice 7.x (3.8+), i.e. no
  walrus-dependent cleverness, no 3.10-only syntax.
* `core.py` contains only document-model code and never imports `dialog.py`;
  that separation is what lets the tests drive `core` directly.
* Errors the user should see are raised as `core.PlanError` with a message that
  says what to do next; anything else is logged to `error.log` and reported.
* Keep the "why" comments. The unusual lines in this codebase exist because of a
  specific measured LibreOffice behaviour, and a well-meaning cleanup that
  removes one of them reintroduces a real bug.

## LibreOffice facts this code depends on

All of these were verified on LibreOffice 26.8.2.2 on Linux. Each one is
reproducible with a script in `dev/`.

### Packaging

1. **`description.xml` dependency spelling.** Use
   `<lo:LibreOffice-minimal-version value="7.0" d:name="LibreOffice 7.0"/>` in
   the namespace `http://libreoffice.org/extensions/description/2011`. An element
   with the *same name* in the 2006 namespace fails with
   `unsatisfied dependencies` whatever value it carries, and
   `OpenOffice.org-minimal-version` is compared against
   `ReferenceOOoMajorMinor` (`4.1` in `program/versionrc`), so asking for `"7.0"`
   there fails as well. `dev/dep_probe.py` walks through every spelling.
2. **Only register what must be registered.** `META-INF/manifest.xml` declares
   `Addons.xcu` (`configuration-data`) and `handler.py`
   (`uno-component;type=Python`). The `plan_impress` package is *not* declared:
   `handler.py` adds its own folder to `sys.path` and imports it normally.
3. **No `com.sun.star.*` imports at module level** in anything the extension
   manager loads. During registration those imports fail
   (`ImportError: No module named 'com'`) and registration is skipped with only
   a warning on stderr — the extension then looks installed but has no menu and
   no error message. Import them inside functions/methods. `handler.py`
   additionally guards `from com.sun.star.task import XJobExecutor` at module
   level and falls back to `object`, because the class definitions must be
   evaluable at registration time.
4. `unopkg` does not replace a running installation: stop the office first, and
   `unopkg remove <identifier>` before `add` when testing packaging changes.

### Menu (`Addons.xcu`)

5. Top-level menus are added with `OfficeMenuBarMerging`. `MergePoint` is a
   **menu path of item commands** separated by backslashes — `.uno:SlideShowMenu`
   puts us after *Slide Show*. `MergeCommand` accepts
   `AddAfter | AddBefore | Replace | Remove`; `MergeFallback` accepts
   `AddPath | Ignore` (`AddLast` is a *toolbar* token and is silently ignored
   here).
6. `MergeContext` and each item's `Context` are matched against the module
   identifier `ModuleManager::identify()` returns for the document model — for
   Impress that is `com.sun.star.presentation.PresentationDocument`. A wrong
   value fails **silently**: the menu just never appears.
7. A submenu node needs `Title` + a `Submenu` child and must **not** carry a
   `URL`; the leaf items need `URL` + `Title` + `Target=_self`.
8. Icons go under `AddonUI/Images`, keyed by the same `URL` as the menu item,
   with `%origin%/icons/…` paths (`%origin%` = the extension's own folder).
9. The configuration is only re-read at startup; after changing `Addons.xcu`
   you must restart the office (`make install` does it).

### Calling into Python

10. Menu items use `service:<implementationName>?<args>` bound to
    `com.sun.star.task.Job`, registered with `unohelper.ImplementationHelper()`
    in `handler.py`. LibreOffice then calls `XJobExecutor.trigger(args)`. This
    is the SDK's own pattern; `vnd.sun.star.script:` URLs are fragile because
    they embed the installed `.oxt` file name and
    `location=user:uno_packages`.
11. **Run the work inline in `trigger()`.** Executing the same document work
    from a Python **worker thread crashes the office** (`free(): invalid
    pointer`, `Unspecified Application Error`, whole process gone). The
    `.uno:MovePageUp/Down` commands are nevertheless asynchronous, so
    `core.insert_page_at()` polls for the index change instead of hoping.
    `PLAN_IMPRESS_DEFER=1` switches to a `com.sun.star.awt.Timer` main-loop
    deferral; keep that path working — it is the debugging tool for dispatch
    ordering.

### The document model

12. **Sections.** `doc.SlideSections` is a
    `sequence<com.sun.star.beans.PropertyValue>` whose values are themselves
    property-value sequences (`Name`, `Id`, `SlideNameList`). Writing it back
    only works when the nested values carry an explicit `uno.Any` type:
    `uno.Any("[]string", tuple(names))` and
    `uno.Any("[]com.sun.star.beans.PropertyValue", inner)`. Plain tuples are
    **silently dropped** — the assignment appears to succeed and nothing
    changes. Empty sections are kept by LibreOffice and are ignored here.
    What the list *means* is the trap: the document stores a **contiguous range
    of positions** and renders it back as names, and the name a page answers to
    is its `LinkDisplayName` (`"Slide 3"`) or the value a client last assigned to
    `page.Name` — **never** the `DrawPages` name (`page3`). So a deck the user
    made in Impress lists its sections as `Slide 3`, `Slide 4`, …, matching
    nothing in `DrawPages`, and comparing the two made *Insert Plan Slides*
    refuse to work on any real document. On a write, each name is resolved to
    the position it names *now*, unmatched names are dropped in silence, the
    ranges stretch over the gaps and the **last section always runs to the end
    of the deck** ("these slides belong to no section" cannot be expressed). All
    of it is printed by `dev/debug_sections.py`; `core.get_sections()` resolves
    names to indexes and `core.set_sections()` takes indexes back.
13. **`XDrawPages.insertNewByIndex(k)` inserts *after* position `k`**, clamps
    `k` to the page count, and can therefore never reach index 0. The container
    has no reorder method. `core.insert_page_at()` compensates: insert, then
    walk the page into place with `.uno:MovePageUp` / `.uno:MovePageDown`.
14. Those move commands act on the slide the **view** has selected, so
    `controller.setCurrentPage(page)` first. `controller.select(page)` does
    **not** work (measured: the page never moves — `dev/debug_move.py`). They
    are also asynchronous, hence the polling in `_wait_for_move`.
15. Insertions do **not** shift section membership: sections must be rewritten
    after every insertion (that is why `insert_plan` recomputes the whole list
    at the end and inserts bottom-up so the pending targets stay valid). Nothing
    identifies a page across such a change either — LibreOffice renumbers the
    automatic `pageN` names by position, so the slide that was `page3` is
    `page4` afterwards (`dev/debug_sections.py` prints it) — hence
    `core._section_with_plan()` computes where the slides *must* have ended up
    and `_check_sections()` reads the list back and refuses to pretend success.
    The assignment drops the section `Id` unless it is sent back, so
    `set_sections()` carries it through.
16. **Deleting a slide that anchors a section corrupts the section list**
    (measured: three sections became two with the wrong slides in them). So
    `remove_plan_slides()` snapshots the cleaned section lists first and
    rewrites them after the deletions. Do not "simplify" that.
17. **Only slides before the first section may be ungrouped.** Writing
    `doc.SlideSections` normalises the lists: a slide that belongs to no section
    and sits *after* the start of the first section is appended to the section in
    front of it (measured with `dev/debug_ungrouped.py`: sections `A=[s1,s2]`,
    `B=[s4]` over six slides came back as `A=[s1,s2,s3]`, `B=[s4,s5]`). Slides
    before the first section do survive, which is what lets a title slide stay
    outside every section while `insert_plan` puts the overview at the first
    section's start.
18. `com.sun.star.presentation.SubtitleTextShape` raises
    `ServiceNotRegisteredException`; `com.sun.star.presentation.OutlinerShape`
    and `com.sun.star.drawing.TextShape` work. `core.BODY_SERVICES` tries them
    in that order.
19. Never test a shape type with `"Title" in shape.ShapeType` — the body
    placeholder's type is `...SubtitleTextShape`, which also contains "Title".
    Use `supportsService("com.sun.star.presentation.TitleTextShape")`
    (`core._is_title`).
20. **`CharHeight` is a point size; every geometry property is 1/100 mm.** Never
    derive one from the other: the original `height / 100` formula produced a
    262 pt heading (`dev/debug_sizes.py` prints the shape, paragraph and portion
    values). `core._master_char_height()` takes the size from the master
    placeholder (44 pt title / 32 pt body in the default master) and falls back
    to `_TITLE_PT`/`_BODY_PT`; `_fit_point_size()` shrinks the list so all
    sections still fit under the heading, and `_UNITS_PER_POINT` (35.28, not
    3528) is the only place the conversion happens.
21. **Do not copy a master placeholder's rectangle blindly.** The default
    Impress master keeps its title placeholder at `y = -32 mm` about two thirds
    of the page tall; used verbatim the heading is drawn outside the slide.
    `core._rect()` takes the rectangle only when it fits on the page and
    otherwise uses the computed fallback. Impress also re-snaps a presentation
    placeholder to the master and auto-grows it, so the rectangle you set is not
    always the one you read back — check the rendered result, not the property.
22. Presentation placeholders **anchor their text in the middle of the box**, so
    a one-line heading floats down into the body; `_make_text_shape` sets
    `TextAnchor` (awt `TOP` = 0) and `TextAnchorKind` (drawing `TOP` = 1) — but
    only when `TextVerticalAdjust` could not be mirrored from the master: with it
    mirrored, the master's own anchoring is the template's and has to survive.
23. Per-paragraph colour is set on the paragraphs of `createEnumeration()`
    (`_paint_paragraphs`), and a plain-text shape created with `setString()`
    treats `\n` as a paragraph break.

### AWT (`dialog.py`)

24. `dialog.Model = model` **raises** (`UnknownPropertyException: ... property
    is readonly`) — use `dialog.setModel(model)`.
25. **Control models must come from the dialog model's own `createInstance()`.**
    That is what `/usr/lib/libreoffice/program/wizards/ui/UnoDialog.py` does, and it
    is the whole reason the form has a layout: such a model keeps
    `PositionX`/`PositionY`/`Width`/`Height`, while one from the service manager has
    *no* geometry properties at all, so every control lands at 0,0 with its natural
    size and the settings dialog is an unreadable pile in the corner.
    `dev/debug_dialog_props.py` prints the two property sets side by side.
26. `XNameContainer.insertByName()` on a dialog model **rejects** the documented
    `sequence<PropertyValue>` carrying a `Servicename` (`IllegalArgumentException`
    in every spelling tried — control or model service name, list/tuple/`uno.Any`,
    with or without geometry, before or after the peer exists:
    `dev/debug_dialog_insert.py`). Insert the model object instead.
27. The dialog's **window size is a model property**: set `Width`/`Height` on the
    dialog model (`Width=140` → a 354-wide window, `dev/debug_dialog_windowsize.py`).
    `XControl::setPosSize` moves the dialog and silently **discards the size**, so
    `setPosSize(..., POS | SIZE)` still leaves the 300x450 default; use it for the
    position only, as `dialog._centre()` does.
28. Those coordinates are **AWT dialog units** — neither pixels nor 1/100 mm. One
    unit is about 2.5 px of peer geometry (measured 2.53 x 2.39 in
    `dev/debug_dialog_units.py`), which puts the form at 176x145 units ≈ 445x367 px —
    the same magnitude as the wizards, which give a label `Height=8`.
29. The two factories have different property sets: the container's own adds
    `PositionX/Y`, `Width`, `Height`, `Name`, `Tag`, `Step`, `TabIndex`,
    `ResourceResolver` and **lacks** `MaxLen`, `TabStop`, `TabPosition`, `Multiple`.
    Those four are therefore not set: the hex fields are validated in `result()`
    and the tab order follows position. `setPropertyValues()` fails *as a whole* if
    one property is unknown, which is why `_apply()` falls back to one by one.
30. A list box only shows a selection when `SelectedItems` travels **with the model
    into `insertByName`**; set on the inserted child it is accepted and then ignored
    by the peer (`getSelectedItemPos()` stays -1 — `dev/debug_dialog_masters.py`).
    Sequence properties need explicit typing: `uno.Any("[]string", ...)` for
    `StringItemList`, `uno.Any("[]short", ...)` for `SelectedItems` (0-based).
    `getControl(name)` exposes a limited method set: `selectItem()`/`selectItemPos()`
    raise on the argument count and there is no `getPropertyValue`.
31. Give every button its **own** `XActionListener`. Deciding which one was pressed
    from `event.Source.Model.Name` failed silently, so OK became a cancel: the
    dialog closed and nothing was saved.
32. `Toolkit.createMessageBox(parent, type, buttons, text)` builds the message
    boxes, with `MessageBoxType` `0|3|4` (message/warning/error) and
    `MessageBoxButtons` `1` (OK) or `5` (Yes/No); `execute()` returns
    `MessageBoxResults` (`6` = Yes). Always `dispose()` in a `finally`, and never
    let a reporting failure swallow the real error. `setTitle()` works on the
    dialog, `setPropertyValue("Title", …)` does not.

### Settings and logs (`config.py`)

33. **The profile comes from the deployment path, not from the office.** Asking
    pyuno is a dead end — `PathSettings.User` and
    `PathSubstitution.getSubstitutedValue()` both raise `AttributeError` there —
    and the old hard-coded `~/.config/libreoffice/4/user` fallback made the
    extension save into a *different* LibreOffice, so pressing OK appeared to do
    nothing. A deployed extension lives under `<profile>/user/uno_packages/...`, so
    `config._profile_from_path(__file__)` reads the profile out of its own path.
    `PLAN_IMPRESS_DATA_DIR` overrides it, which the `dev/` scripts need because
    they run outside the office and have no deployment path.

### Out-of-process test scripts

34. A remote document proxy does **not** expose `getComponentContext()`, so
    `core`'s functions take an optional `ctx` argument (`insert_plan(doc,
    settings, ctx)`). Keep it optional — the in-process Job relies on the
    default — and pass the connected context from tests.
35. Tests need a controller and a frame (moving slides and dispatching commands
    both require one), so they load documents **non-hidden** against the UI-mode
    dev office. `lo.open_doc(..., hidden=False)` waits for the controller.
36. The office logs to `out/soffice.log`. The extension's own logs are
    `loprofile/user/planimpress/error.log` (always written) and `debug.log`
    (only with the `debug` marker file in that folder, or
    `PLAN_IMPRESS_DEBUG=1`); the *Toggle Debug Log* menu item flips it.
37. The UI itself can only be checked on a real display:
    `Xvfb :98 -screen 0 1440x900x24` plus a window manager (`openbox --replace`;
    there is no `marco` here — fact 76), `DISPLAY=:98 make install`,
    `python3 dev/open_fixture.py`, then drive the menu with
    `xdotool mousemove X Y click 1` and capture with `scrot -o`.
    `dev/render_plan.py` renders the generated slides to PDF/PNG instead, and
    `dev/show_plan.py` inserts the slides and puts one in front of the controller
    for the screenshot. Both are how the settings dialog was finally confirmed —
    assertions had passed the whole time it was unusable.

### The footer band (`core.apply_footer`)

38. **The footer belongs to the slide, not to the document.** `FooterText`,
    `DateTimeText`, `DateTimeFormat`, `IsDateTimeFixed`, `IsFooterVisible`,
    `IsDateTimeVisible` and `IsPageNumberVisible` are properties of the *page*
    (`com.sun.star.presentation.DrawPage`; they are the ODF
    `presentation:display-*` flags and `draw:footer-text`). On the document they
    raise `AttributeError`, and so do `page.StyleName` and
    `doc.StyleFamilies["PageStyles"]` — `dev/debug_footer_switches.py` prints
    where they really are. A page from `insertNewByIndex` has all of them empty,
    which is what made the generated slides footer-less.
39. **Switched on is not the same as printing.** A fresh deck reports
    `IsFooterVisible=True`, `IsDateTimeVisible=True`, `IsDateTimeFixed=True` with
    both texts empty, and prints nothing; `fixtures/sections_no_footer.odp` is
    that deck, and `core._footer_prints()` is what keeps a footer from being
    invented there. A date that is a field (`IsDateTimeFixed=False`) does print —
    today's date.
40. **Copying those properties is enough for a deck authored in Impress**, because
    the master page's own placeholders do the drawing — and a `FooterShape`
    created empty on the page neither draws nor hides anything
    (`dev/debug_footer_render.py` exports the variants next to each other). A deck
    written elsewhere keeps a real frame per slide instead
    (`presentation:class="footer"` in `content.xml`); those are recreated by
    `_mirror_footer_shapes`, with the master's rectangle and character height.
41. **The date and the page number are text *fields*, not characters.** Copy them
    by inserting the field object — `text.insertTextContent(cursor,
    portion.getPropertyValue("TextField"), False)` — and it prints the number of
    the slide it now sits on, so every plan slide gets its own. `getString()` of a
    field portion answers with the placeholder stored in the file (`<footer>`,
    `<number>`) or with whatever the last layout pass painted: never assert on it,
    render instead. `core.FOOTER_FIELD_SERVICES` recreates a field from its service
    when the object cannot be reached.
42. All four band shapes — `com.sun.star.presentation.HeaderShape`,
    `DateTimeShape`, `FooterShape`, `SlideNumberShape` — *are* creatable, unlike
    `SubtitleTextShape` (fact 18), and neither `XShapes.add()` of an existing shape
    nor `createClone()` copies one between pages, so they have to be built
    (`dev/debug_footer.py`). A freshly created one already holds its own field, so
    clear the shape before putting anything into it.
43. `core.footer_source()` picks the first non-generated slide whose band prints
    something, or `None`; `insert_plan` looks it up once and passes the same slide
    to every `build_plan_slide`, so all plan slides agree with each other.

### The settings dialog's own look (`dialog.py`)

44. **The dialog sets its own text size.** Control models take `FontHeight` in
    points, and at the original 10 the labels measured 13 px of ink where a Plan
    menu item measures 14 px — the report was "text on the setting pane is smaller
    than the menu text". `dialog._FONT` is 12, which measures 17 px (12 px of caps
    plus the mnemonic underline): the same face the menus use. `dev/measure_text.py`
    screenshots the dialog and the open menu and prints both heights, because no
    property assertion can see this.
45. Rows are spaced by `_ROW_STEP = _FIELD_H + _ROW_GAP`, i.e. a row is its field
    plus clear air under it. Spacing each row by a fixed 14 units for 12-unit fields
    left the next label 2 units under the previous field, which is what "the entries
    are too cramped" meant. Both are asserted in
    `tests/run_tests.py dialog_text_is_readable_and_rows_are_not_cramped`.
46. Nothing on a control peer tells you what font it renders: `FontDescriptor`,
    `FontName` and `FontHeight` are all absent from the peer proxy
    (`dev/debug_font.py` prints `<none>` for every one). Judge text size from
    pixels — `dev/measure_text.py` counts the bright rows of a screenshot (this
    theme is dark, so text is the *light* pixels: thresholding for dark pixels
    measures the background and reports every row as text).

### Verifying a change (both agents hit both of these)

47. When you check that a test fails without the fix by editing `src/` and putting it
    back: if the edit and the restore land in the same second and the file ends up the
    same size, the `.pyc` keeps the mutated bytecode and the "restored" run still
    fails. Remove `__pycache__` (or `make clean`) before trusting such a run.
48. `dev/stop_lo.sh` kills soffice, so a document of the run just killed keeps its
    `.~lock.<name>#` file. The next `loadComponentFromURL()` then waits on a modal
    "the document is in use" dialog and the script hangs without printing anything;
    the dialog also survives the client and wedges every later load until the office
    is restarted. `dev/lo.py:clear_lock()` removes it before loading, and a hang in
    `open_doc` means restarting the office, not the script.

### The template's own look (`core.py`)

A generated slide has to look like the deck's own slides were *edited*. Everything
below was measured with `dev/debug_numbering.py` (one PDF, a slide per variant) and
`dev/debug_style_source.py` (what the masters, the deck's own slides and the
generated ones say about themselves, side by side) on LibreOffice 26.8.

49. **Inherit the master's list level and write only `NumberingType`.** Copy all
    ten levels of the master content placeholder's `NumberingRules` and patch the
    first one: a rules object built from scratch gives the digits a font, a size, a
    gap and a colour of their own, and they look pasted onto the slide.
    `NumberingType` has to be the **integer** of `NumberingType.ARABIC` (`4`) — `1`
    is `CHARS_LOWER_LETTER`, which is the "a. b. c." the first attempt rendered, and
    a value pyuno marshals from a string arrives as 0, i.e. no label at all — and
    the level goes back as `uno.Any("[]com.sun.star.beans.PropertyValue",
    tuple(level))`. `Prefix` and `Suffix` are literal text: `"%1."` prints `%1.`.
50. **The properties that describe the glyph have to be re-asked for.**
    `BulletRelSize` sizes the *character* the template draws — the fixture's master
    asks for 45 % of the text height, which is an unreadable digit — so when the
    label is a special character (`NumberingType` 6 or 8) it becomes
    `max(inherited, 100)`. The label's column likewise: two slides whose level read
    exactly the same (`LeftMargin` 1200, `FirstLineOffset` -1200) rendered with and
    without a gap, and what separated them was the **paragraph's**
    `ParaLeftMargin`/`ParaFirstLineIndent`, so those are set from the level's indent
    or the digit sits on the text (`1Introduction`). `SymbolTextDistance` is no
    help: writes to it are ignored and it mirrors `FirstLineOffset`.
51. **Dim a row's number with a rules object of its own.** The label is painted with
    the level's `BulletColor`, so one copy of the rules per paragraph differing in
    that one property dims the sections that are not the current one — and the list
    still counts 1, 2, 3 across the different rule objects. The `Bullet*` properties
    of a *paragraph* are refused outright (`BulletColor`, `BulletChar`,
    `BulletNumberingType`, `BulletRelSize` all raise), which is why the rules have to
    be copied. A template that fixes no bullet colour (`-1` = follow the text) gets
    the highlight colour on the current row.
52. **Mirror the template placeholder's characters onto the shape *and* onto its
    paragraphs, from its first paragraph.** A shape from `createInstance()` comes in
    the page style's font, and a *paragraph* of an outline placeholder comes in the
    page style's outline level — `CharWeight` 150 where the template's own
    placeholder says 100, so the list rendered bold next to the deck's own slides.
    The source is the template placeholder's **first paragraph** (`_first_paragraph`)
    when it has one and its shape otherwise: on a real master the two disagree, and
    the paragraph is the outline level the deck is drawn with.
    `core.CHAR_ATTRIBUTES` is the shape's list, `core.PARAGRAPH_ATTRIBUTES` the
    paragraph's (no `CharStyleName`, which a paragraph does not have; no
    `CharHeight`/`CharColor`, which are ours).
53. **Setting `page.Layout` creates the placeholders.** `page.Layout = 2` on a fresh
    page hands back a `TitleTextShape` and an `OutlinerShape` of its own, so adding
    shapes without looking for them yields four; `_ensure_placeholder()` reuses what
    is there. No dispatch route does it better: `.uno:AssignLayout?Layout:short=2`,
    `.uno:AppendPage` and `.uno:InsertPage` are measured no-ops. The layout is
    therefore the *first* thing `build_plan_slide` does after clearing the page, and
    `apply_footer()` runs right after it: assigning a layout re-deals the
    placeholders, so a footer frame mirrored onto the page before it is at the mercy
    of that step.
54. **The deck's own slides are the template; the master page is the fallback.**
    `_style_source()` asks the slides first (`_deck_placeholder`) and the master
    only where no slide has anything to copy, because a slide keeps the box and the
    characters it was given and the two disagree on any deck somebody worked on —
    measured on a deck off the disk, whose master placeholder says `1800,1500`
    `24400x1040` at **32 pt** while its six content slides are all at `1800,1474`
    `24400x1094` at **31 pt**: taking the master produced a heading a point larger
    than the deck's own, a few tenths of a millimetre away from it. The value the
    slides *agree on* wins (they are counted per rectangle-and-look), which is what
    keeps one hand-edited slide, or the cover slide that is usually first, from
    moving the generated ones; `dev/debug_style_source.py` prints the three sets
    side by side.
55. **A presentation placeholder's characters live on its paragraphs.** A master's
    content placeholder keeps **one paragraph per outline level**, so its first
    paragraph is level 1 and is what the slides paint with; the shape's own
    `CharHeight` is only the default underneath it (`32` against the paragraph's
    `31`, `20`/regular against `21`/semibold on the deck above). Ask the paragraph
    first (`_master_char_height`, `_first_paragraph`) — on the shape's value the list
    came out smaller and lighter than the deck's own body text.
56. **The heading has to be measured where it *paints*, not by its box.**
    Presentation placeholders anchor their text in the middle of the box, so a
    template box twice as tall as its one line leaves the text in the middle of the
    box; the list only has to clear *that*. `_heading_bottom()` takes the anchor
    (`_text_anchor`, read back from the shape after mirroring) and returns the bottom
    of the painted line — box top + line for `TOP`, box top + (box + line)/2 for
    `CENTER`, box bottom for `BOTTOM`. Comparing against the box's top let the list
    overlap the heading on the fixture (its title box spans 1575..4725 while its
    body box starts at 3685).
57. **The deck's numbering format lives with the heading, not with the body.** The
    first `NumberingType` that is worth copying is the content level's own; where that
    level draws a glyph instead of counting, the deck is asked in the order deck
    content, deck **title**, master content, master title (`_label_sources`) — a
    template keeps its numerals in the heading and its decoration in the body, and on
    the deck this was measured on the content level is `CHAR_SPECIAL` with an OpenSymbol
    arrow while the title level counts `ROMAN_UPPER` with a `.` suffix
    (`style:num-format="I"` in `content.xml`). Taking the label from another level
    takes its `Prefix` and `Suffix` with it — the text around the number is the format
    as much as the numerals are — but *not* its `LeftMargin`, `FirstLineOffset` or
    `BulletRelSize`, which belong to a heading. The measured `NumberingType` values are
    `CHARS_UPPER_LETTER 0, CHARS_LOWER_LETTER 1, ROMAN_UPPER 2, ROMAN_LOWER 3, ARABIC 4,
    NUMBER_NONE 5, CHAR_SPECIAL 6, PAGE_DESCRIPTOR 7, BITMAP 8`; nothing in
    `(6, 8, 0, 5, 7)` counts (`_uncounted_labels`), so only those get digits. The size
    and column correction of fact 50 belongs to *that* case alone: when the label is the
    template's own, whatever it asks for stays.

### Working on two documents in one office (`insert_plan`)

58. **The settings are per profile, so the master they name is usually another
    deck's.** A `master` that this document has no master page for is *not* an error —
    it means "the deck's own", exactly like the empty setting (`_master_page` falls back
    to `_default_master`). Refusing there is the report "inserting plan slides does
    nothing in the second deck until I open *Settings*": the office logs it as
    `Master slide 'Blue_Curve1' no longer exists`, and *Settings* appeared to fix it
    because its master list is filled from the deck in front, so saving there wrote a
    name that deck has. `insert_plan` reports which master it used and whether the
    settings named one this deck has (`master`, `master_named`). `_default_master()`
    counts the masters of the deck's *own* slides and ignores generated ones, or the
    second run picks what the first one's slides used instead of what the deck uses.
59. **`insert_plan` is all-or-nothing.** Everything that can refuse is settled before
    the deck is touched — the master above all, which used to be resolved once *per
    generated slide*, i.e. after pages had been inserted — and any later failure goes
    through `_drop_pages()`: every generated slide out (all of them, not just the ones
    that were reported inserted: `insert_page_at` raises *after* `insertNewByIndex`) and
    the section list written back the snapshot taken after the initial
    `remove_plan_slides()`. A deck left half-inserted has empty slides in it and sections
    that no longer match its slides, and the next run then cleans a wreck instead of a
    deck — measured as three sections coming back as one (`dev/debug_two_documents.py`,
    `dev/debug_rollback.py`). It is *not* the move commands losing the second deck's
    page: `dev/debug_move_race.py` inserts and removes the plan slides over six rounds
    with another deck open and loses nothing, worst case one dispatch round.
    `remove_plan_slides()` does **nothing at all** when there is nothing to delete,
    because writing `SlideSections` normalises the deck (fact 17) and a run that was
    only looking for old slides must not move a boundary.

### The dev office under a long test run

60. **A long UI session takes the office down, and it is not the extension.** Once a
    few dozen documents have been loaded, moved and closed, soffice dies of
    `free(): invalid pointer` / `Fatal exception: Signal 11`, the stack going from
    `libbinaryurplo` through `cppu::OWeakAggObject::release` into `libeditenglo` — pyuno
    letting go of a text object whose document is already gone. It is LibreOffice under
    load, not this code: running the *committed* suite a second time in the same office
    process does it too, on documents the extension never sees. Where the death lands is
    a matter of luck, and everything after it fails with `cannot connect to soffice`, so
    `tests/run_tests.py` notices the office has gone (`lo.is_alive()`, `lo.died()` — the
    socket stays open for a moment after the process starts to die, which is why both the
    `/proc` command line and the port are checked), starts a new one and gives that test
    its one retry; a test that fails twice has failed. Nothing is hidden: the run ends
    with `office restarted N time(s)`. One signature says "that was the office and not
    the code": a `cannot get value DrawPages` / `... value Count`
    (`UnknownPropertyException`) raised from inside `core` on a document the same run
    read a moment earlier — a proxy whose office is gone. It landed on the same
    document-heavy test twice in a row here, both attempts inside the wreckage of a
    death, and the same suite was green before and after on a freshly started office
    (`dev/start_ui.sh`); restart the office and re-run before believing such a failure.
61. **A load right after a start answers with a *null* document.** The office answers
    its UNO socket before the desktop can create a document, and
    `loadComponentFromURL()` then returns a null proxy instead of raising; the caller's
    first property read is the unhelpful `cannot get value DrawPages`. `lo._load()` waits
    for the proxy to answer `getURL()` before handing it over.

### The colour picker (`picker.py`, `palettes.py`)

62. **There is no colour picker to reuse.** `ColorPicker`, `ColorBox`,
   `ColorPickerDialog` and any `XColorPicker` are absent from
   `program/types/offapi.rdb`, and the only `ColorListBox` string in there is a
   `com.sun.star.inspection` enum literal for the Object Inspector, not a control
   (`dev/probe_api.py` asks for each spelling by hierarchical name and finds
   nothing). So the widget is assembled here out of the same control models the
   settings dialog uses. Nothing in the API exposes the office's palette list
   either — see the next fact.
63. **The palettes are the `.soc` files, and their XML namespaces disagree.**
   LibreOffice keeps every colour table as
   `<installation>/share/palette/<name>.soc` (`standard`, `libreoffice`,
   `material`, `tonal`, `html`, `chart-palettes`, `compatibility`,
   `freecolour-hlc`, …) plus the user's edited copies under
   `<profile>/user/config/`, and reads colours from `draw:color` attributes.
   `standard.soc` and `tonal.soc` use the old `http://openoffice.org/2000/drawing`
   namespace while `libreoffice.soc` uses the OASIS one, so asking ElementTree for
   a fixed `{uri}color` silently returns nothing and the palette simply never
   appears; `palettes._attribute()` looks attributes up by *local* name. Read the
   user's directory first and `setdefault` by name, or a palette the user edited
   is quietly replaced by the shipped one.
64. **A control's paint listener is never called; its mouse listener is.**
   `dev/probe_paint.py` attaches both to a control in a dialog and drives it with
   `xdotool`: `mousePressed` arrives with pixel coordinates, `paint` never fires.
   The grid therefore cannot be drawn — it is `picker.CELLS` (60) controls with
   `BackgroundColor` set, one per square (which control: fact 77). What the mouse
   listener does buy is the hover read-out and the click.
65. **`UnoControlButtonModel` has no `Border`, `BorderColor` or `BorderLine2`.**
   Setting one is not ignored, it is an error `dialog._apply()` collects as a
   warning and the tests fail on. It does have `BackgroundColor`, `TextColor`,
   `TextLineColor`, `HelpText` (a cell's colour name, so hovering says what the
   square is) and `DefaultButton`. `UnoControlPanelModel` and
   `UnoControlMessageBoxModel` cannot be created from a dialog model at all —
   `createInstance()` answers `None` — while `UnoControlImageControlModel` can.
   `UnoControlFixedTextModel` and `UnoControlImageControlModel` **do** have `Border`
   and `BorderColor` — which is what makes a colour showable without a button's
   bevel (fact 77).
66. **An exception raised inside a listener disappears.** The office does not carry
   a Python traceback across the listener boundary: `out/soffice.log` stays empty
   and the widget simply looks dead — a swatch that opened nothing was a
   `TypeError` for ten minutes. `SettingsDialog._pick_colour()` therefore catches
   everything and writes `traceback.format_exc()` to the debug log. Do the same in
   any new listener.
67. **A palette is always `[(name, colour), ...]`** — the shape `load_palettes()`
   returns — because a cell is built by unpacking each entry. `deck_palette()` and
   `recent_palette()` label the colours they invent with their hex value. A bare
   int in either is fact 66's invisible crash, which is what
   `recent_palette_offers_pairs_of_name_and_colour` and the assertions in
   `deck_palette_lists_the_colours_the_deck_uses` are there to catch.
68. **Cells past the end of the palette have to be switched off, and only after
   `createPeer`.** `setVisible()` talks to the peer, so `show()` calls
   `_paint_cells()` after `_peer()`; before the fix a 5-colour palette left 55
   squares painted in the colour being edited, looking pickable and picking
   something else. Paging (`<`, `>`) exists because no scrollable container's model
   can be created and `freecolour-hlc` has 240 colours.
69. **The picker is a popup of one fixed shape.** Every control — the sixty squares,
   both captions, the header, the read-out and the buttons — is created once at its
   final rectangle, from `full_bands()` (the recent row plus a *whole* page), and
   only colours, labels, `Enabled` and visibility change at runtime, because geometry
   does not (fact 70). `flat_cells()` therefore pads each group to whole rows: with a
   three-colour recent group the palette's first colours otherwise landed in the
   *recent* row's squares. `page_size(recent) = CELLS - COLUMNS` says what that row
   costs the page.
70. **Control geometry does not follow the model after `createPeer`; colour and
   words do.** Writing `PositionX`/`PositionY` to a control model once the peer exists
   changes the model and leaves the pixels where they were — measured by hiding a
   caption, moving it and showing it again, and by the second group's caption ending up
   painted behind the palette selector. `BackgroundColor`, `Label`, `HelpText`,
   `Enabled`, `setVisible()` and the **dialog model's** `Width`/`Height` do take effect.
   An `XControl` has no `getPosition`; ask its **peer** (`getPeer().getPosSize()`,
   pixels, 2.53 x 2.39 per dialog unit). `dev/probe_picker_peers.py` prints model units
   and peer pixels side by side, which is the only way to tell a wrong layout from a
   wrong assumption.

### Message boxes (`dialog.message`)

71. **There is no message box to reuse.** On LibreOffice 26.8 the toolkit exposes
   `XToolkit2::createMessageBox` with **five** parameters — `(XWindowPeer,
   MessageBoxType, long, string text, string title)` — where `XToolkit` up to
   LibreOffice 7.x had four. The four-argument call raises `IllegalArgumentException:
   expected 5, got 4` before a window exists; with the fifth supplied a window *does*
   appear and paints nothing but its OK button — 400 characters of text produce the
   same empty strip (`dev/probe_message_box.py`, `dev/probe_debug_toggle.py`). So
   *Toggle Debug Log does nothing* was a command that ran, flipped the marker and
   showed an empty box, and every message the extension shows is now
   `dialog.message`: a top-level `UnoControlDialog` of the same make as the settings
   dialog. Fact 32's `createMessageBox` recipe is dead; keep `setTitle()` and the
   `dispose()` in a `finally` from it.
72. **A `FixedText` wraps nothing.** `UnoControlFixedTextModel` has `MultiLine` but
   **no** `WordWrap`, `TextAlign`, `Mnemonic`, `Decorative` or `MaxLen` (each one
   `UnknownPropertyException` — `dev/probe_mnemonic.py`), so the text is wrapped in
   Python (`dialog.box_lines`, `break_long_words=True` because a log path is one long
   word, `break_on_hyphens=False` because splitting a path at a hyphen makes it look
   like two paths) and one label per line, which is also what fixes the window height.
   The office draws a **mnemonic underline under the first letter of the label that
   stands in front of an edit field** — the way a form underlines the label *of* a
   field — and the buttons carry theirs too, which is the office's own look. No
   property switches it off (the absent `Mnemonic`/`Decorative` above), so the
   picker's read-out begins with a space and an empty label sits in front of the hex
   field to take the stroke (`picker.readout`, `picker.bottom_specs`, fact 81;
   `dev/probe_underline.py` photographs the six variants).
73. **The box answers codes of our own, and they have to be asked for.** `RESULT_OK`
   1, `RESULT_CANCELLED` 0, `RESULT_YES` 6, `RESULT_NO` 2 — 6 is what the office's box
   answered here and what `confirm()` still compares against. Enter and Escape need a
   `XKeyListener` on the **peer**: `dialog.getPeer()` *before* `createPeer` answers
   None, so a listener attached at build time was attached to nothing and Enter worked
   only because the office acts on `DefaultButton` itself — and `DefaultButton` on the
   secondary button made every box answer "cancel" to Enter. `_build_box()` is the box
   without `execute()`, which is how the codes are tested at all: a modal box cannot be
   looked at from the inside.

### Seeing what a widget actually painted

74. **A screenshot has to be taken synchronously.** `os.spawnv(P_NOWAIT, ..., scrot)`
   returns before the pixels are grabbed, so every shot showed what the *next* step had
   already done: one and the same colour chip looked blue in one screenshot and black in
   the next, and the investigation that followed was about a bug that did not exist.
   `dev/probe_picker_look.py` waits for `scrot` and then samples the **pixel** of the
   swatch rather than trusting the eye, which is also how the hover read-out was found
   to be stale (fact 75).
75. **A peer is not told when its model changes.** Writing `Label` or `BackgroundColor`
   after `createPeer` leaves the pixels alone. `dialog.updateWindow()` does not exist
   (`AttributeError`); the peer has `invalidate(flags)` and wants a
   `com.sun.star.awt.WindowPaintFlags` — `1` (`PAINT`) repaints the window and leaves
   the *controls* showing what they showed before, which is how the read-out under the
   grid kept the colour the dialog was opened with however often the pointer moved.
   `picker._refresh()` invalidates the dialog peer with `3` (`ALL`) and then each
   control's own peer.

### The dev office's window manager

76. **There is no `marco` on this machine; `openbox` does the job** (`dev/start_ui.sh`
   runs it). Without a window manager a top-level `UnoControlDialog` lands at 0,0 and
   partly off the screen, so `dialog.centre()` appears not to work: it moves **X**
   correctly and the Y the WM chooses is the one you see. Fact 37's `marco --replace`
   should be read as "any window manager".

### Showing a colour (`picker.py`, `dialog.py`)

The report was "a very ugly perspective-style border around the color ... both in the
palette and in the option screen", plus "I see twice the title, once in the dropdown
menu and once under it", "the text is cramped" and "pages (1/1 is not centered".
Every one of them was measured rather than guessed (`dev/probe_swatch_look.py`,
`dev/probe_picker_peers.py`, `dev/probe_underline.py`), because all four are about
pixels no property assertion can see.

77. **A colour is *drawn*, on an image control — never on a button, never on a coloured
   label.** The "perspective-style border" is the theme's **button bevel**:
   `dev/probe_swatch_look.py` photographs one candidate per row and finds a button's
   colour ringed by `#000E39` above and to the left and `#5F8EB9` below and to the right
   — dark on one pair of sides, light on the other, which is a raised edge and is what
   the eye calls perspective. A button model has no `Border` to switch it off with
   (fact 65). A label is the next guess — it paints `BackgroundColor` flat and does take
   a `Border` — and it fails the *second* report ("look how the default palette colors
   are drawn, with a thin white border on a dark theme, and think dark border and a
   white theme"), because its line can only be the theme's own (fact 78) and a black
   square therefore had no edge at all. What is painted is an
   `UnoControlImageControlModel` carrying a PNG written here (fact 82): the sixty squares
   of the grid, the chip under them and both swatches beside the hex fields all get their
   properties from one place, `picker.swatch_props` — `Border` 0 (the line is in the
   picture), `ScaleMode` fill, `Tabstop` False, `Tag` the hex value, and
   `BackgroundColor` still the colour, which is what shows if no bitmap can be made.
78. **`BorderColor` is accepted and ignored, in every `BorderStyle` there is.**
   `dev/probe_border_colour.py` puts twelve swatches on the screen — each `Border` value
   from 0 to 6, with and without `BorderColor = 0xFF0000` — and photographs them:
   `Border` 0 paints no ring at all (the dialog's own `#383C4A` shows through) and 1
   through 6 all paint the same `#2B2E39`, the theme's line colour, with **0 of 180**
   ring pixels red. Asking for a border colour is harmless and achieves nothing, so do
   not spend time on it or write a test that expects the colour that was asked for: the
   line has to be drawn (fact 82).
79. **A colour control has no action source, so a click on a colour is `mouseReleased`.**
   `addActionListener` on the control of a `UnoControlFixedTextModel` or an
   `UnoControlImageControlModel` raises `AttributeError` (probe: eight times, once per
   candidate); only a button fires `actionPerformed`. Both *do* deliver `mouseReleased`
   and `mouseEntered` — `dev/probe_swatch_ring.py` drives them with `xdotool` at the
   window's real screen position (the window's own peer answers `0,0`, fact 76, so a
   pointer coordinate taken from a child's `getPosSize()` is only right once the window's
   own position is added: an earlier probe moved the pointer to the top-left of the
   *screen* and concluded wrongly that an image control answers nothing). `picker`'s
   `Cell` listener and `dialog`'s `Swatch` listener therefore take the click from
   `mouseReleased` and the hover from `mouseEntered`, both wrapped because of fact 66,
   and the image control is given `Tabstop = False` so a swatch cannot be tabbed to and
   the hex field beside OK stays the keyboard route to a colour.
80. **The palette's name is said once, by the selector above the grid.** `grid_bands()`
   returns `(None, colours)` for the palette page: a caption repeating what the
   dropdown already shows is the duplicate title that was reported, and `_paint_cells()`
   switches such a caption off rather than leaving it blank. A caption that *does*
   exist is reserved **above** its rows (`layout()`: `_CAPTION_GAP` of clear air, then
   `_CAPTION_H`, then the squares) — the first one used to start three units inside the
   selector row, which drew the tops of its letters behind the dropdown, and that is
   "the text is cramped". Both are only fixable at build time, because geometry is
   frozen once the peer exists (fact 70); `pager_geometry()` centres the page indicator
   between the arrows by arithmetic for the same reason, sizing its box for the widest
   string any palette can answer with (`ColourPicker.all_pages()`, `_PAGE_CHAR_W`)
   since a `FixedText` has no `TextAlign` (fact 72).
   `tests/run_tests.py::picker_paints_nothing_on_top_of_anything_else` is what keeps
   the whole popup free of two controls in one place.
81. **The label directly in front of an edit field gets a mnemonic underline.**
   `dev/probe_underline.py` photographs six variants of one line: a read-out before an
   edit is drawn with a stroke under a letter, the same read-out with an empty label
   between it and the field is clean, and a read-out before a button or on its own is
   clean too. The office picks the label *preceding* an edit as that field's label and
   underlines its first letter, and there is no property to say otherwise (fact 72).
   `bottom_specs()` therefore inserts the invisible `hex-label` before `hex`; without
   it "#1F4E79" looked like a broken glyph.
82. **The picture is drawn here and handed over as a `Graphic`.** `UnoControlImageControlModel`
   has `Graphic`/`DefaultGraphic` (an `awt.XGraphic`, `None` by default), `ImageURL`,
   `ScaleMode` and `ScaleImage` — and **no** `ImagePosition`, `ImageData` or `ImageScale`
   (`dev/probe_swatch_bitmap.py` prints what setting each one does: nothing). `ScaleMode`
   is `0` natural size, `1` proportional, **`2` fill** (`ImageScale` is then ignored) and
   `3`/`4` paint nothing; `swatch.bitmap_size()` is `4x3`, which a fill stretches to any
   rectangle without resampling a single pixel of the ring. The PNG itself is written by
   `swatch.png_bytes()` out of `zlib` and `struct` — LibreOffice ships no image library —
   and reaches `GraphicProvider.queryGraphic()` through a `com.sun.star.io.Pipe` whose
   `writeBytes()` wants a **signed** `sequence<octet>` (`x < 128: x else x - 256`; the
   unsigned bytes `bytes`/`bytearray` are marshalled as a `[]string` and the call fails),
   with `closeInput()` before asking. No temporary file: an extension writing to disk to
   paint a square is what the user would rightly object to. `swatch.graphic()` caches by
   `(colour, size)`, `SwatchListener`/`Cell` set `Graphic` on the *control model* after
   `createPeer` — which, unlike geometry (fact 70), does repaint.
83. **The office will not say whether the theme is dark, so the desktop is asked.**
   `Theme::getSettings()` and `XStyleFacility` are absent from `offapi.rdb`; the two
   configuration spellings that look right, `/org.openoffice.Office.Common/Theme` and
   `/VCL/Properties`, raise `UnknownPropertyException`, and `/org.openoffice.Office.Common/Appearance`
   answers `FontAntiPlacement=0 ThemeTone=0` on a clearly dark office — a default, not an
   answer (`dev/probe_theme.py`; `ConfigurationUpdate` cannot be opened at all, and there is
   no theme enum in the type repository). So `swatch.theme_is_dark()` reads what the desktop
   itself configures: `~/.config/gtk-3.0/settings.ini` (`gtk-application-prefer-dark-theme`,
   a `gtk-theme-name` ending in `-Dark`, or `Arc-Dark`), `~/.gtkrc-2.0`, `~/.config/kdeglobals`
   (`[KDE-Gen] Theme=…-dark`) and `GTK_THEME`, with `PLAN_IMPRESS_THEME=dark|light` as the
   override the `dev/` probes use. Nothing to read means `None`, and then **each swatch gets
   the ring that contrasts with its own colour** (`ring_colour`: `#F2F2F2` under a luminance
   below 0.55, `#4D4D4D` above — the luminance is the sRGB one, `/12.92` below the 0.03928
   knee and `((c+0.055)/1.055)^2.4` above it), which is the behaviour on any Linux desktop
   whose settings this code cannot parse and the only one that can never paint a black
   square with no edge on a black dialog.
84. **The chooser is as wide as the longest palette name it has to show, measured in
   pixels.** `picker` measures its dropdown rather than guessing: `selector_width()` is
   the widest entry at `_LIST_CHAR_W` units a glyph plus `_LIST_CHROME_W` of the
   `Popup` control's own frame and arrow — **3.1** and **22**, from
   `dev/probe_selector_fit.py`, which photographs every name twice: in a `FixedText`,
   where nothing can cut it, and in a dropdown at the width in question ("In this
   presentation" is still cut at 74 units and whole at 78). The trap is measuring one
   name: the same probe finds 2.79 units a glyph for "In this presentation" (mostly
   narrow letters) and **3.10** for "Recently used", and the constant was 2.8, taken
   from the first alone, which is what cut the second. `content_width()` takes the
   grid's width and the header row's — selector, gap, two arrows and `_PAGER_AIR` (6
   units) of clear air on each side of the page indicator, reserved *there* as well as
   in `pager_geometry()`, or a window widened for a name just moves the crowding into
   the indicator ("(1/1) is still too close to < and >") — `grid_x()` centres the
   squares in what is left, and `page_label_width()` reserves the widest page count
   `all_pages()` can answer with. All of it is computed **before** `createPeer`,
   because geometry does not move afterwards (fact 70) — the tests over it are
   `the_chooser_is_wide_enough_for_the_names_it_shows` and
   `picker_paints_nothing_on_top_of_anything_else`.

85. **A colour is square in *pixels*, and a dialog unit is not square: 2.53 x 2.39.** A
   control that is `n x n` units is a rectangle on the screen — the 9 x 7 units a square
   of the grid used to be photographs as 23 x 17 px, and the swatch beside a hex field in
   the settings dialog was 22 x 12, a strip ("the color sample must be exact squares, not
   rectangles"). `swatch.square_units(width)` is the rule and every colour carrier is
   sized with it: `picker.CELL_W`/`CELL_H`, `picker._SWATCH_W`/`_SWATCH_H` and
   `dialog._SWATCH_W`/`_SWATCH_H` all paint 33 x 33 px (13 x 14 units). The candidates
   are photographed, not calculated, by `dev/probe_picker_ink.py`: 9x7 → 23x17, 11x12 →
   28x29, 13x14 → 33x33, 14x14 → 35x33, 16x17 → 40x40. Two more reports are answered by
   the same screenshot: touching squares read as one block of colour rather than as ten
   choices, so the grid separates them by `_CELL_GAP` (2 units ≈ 5 px, and 7 px is what
   is clear between one colour's block and the next) the way the office's own
   font-colour dropdown separates its swatches; and the field a colour is typed into
   needed `_HEX_W`, having borrowed the button's 26 units until the probe painted
   "#1F4E79" into fields of four widths and watched the ink grow 49, 54, 62, 64 px and
   stop there — seven characters, because `config.hex_to_color` accepts the leading `#`
   a user types ("the field ... is a bit too narrow"). The probe anchors the client area
   on a square painted `#7FFF00`, because the window's peer answers `0,0` (fact 76) and
   the desktop here is the same grey as the dialog. The tests are
   `a_colour_is_a_square_of_pixels_and_never_a_strip`,
   `the_grid_leaves_clear_air_between_its_squares`,
   `colour_squares_are_square_and_apart_on_the_screen` (the peers, not the specs) and
   `the_hex_field_is_wide_enough_for_the_value_it_shows`.

### The section-name box (*Insert Section Titles*)

`core.apply_section_titles` writes each slide's section name into a plain text box on
that slide; `core.remove_section_titles` takes the boxes away again. The ten things
below are why the code is shaped as it is.

86. **A box is recognised by its name's *prefix*, never by the whole name.** Duplicating
    a slide copies every shape it had, **name included**, and LibreOffice only appends a
    counter: the box `PlanImpress:SectionText:Slide:1` comes back as
    `PlanImpress:SectionText:Slide: 1` (the space is the office's, `dev/debug_section_titles.py`
    prints it). Matching the exact name is therefore the report "the section header is
    not detected when a slide is duplicated": the copy is not seen, and a second box is
    painted over it. The position in the name is decoration for logs and macros, and is
    rewritten on every run so a slide that moved says and names the section it is in
    *now*. `SECTION_TEXT_PREFIX` is the one thing `_is_section_box` compares.
87. **The label is a running head *above* the heading the slide already has.** Placing it
    between the heading and the content measured as `pdftotext -bbox` 56.4–92.1 pt against
    a heading at 64.7–113.8 pt — the bands overlap by 27 pt and the two print through each
    other; only the fixture's *centred* heading had kept that invisible. So
    `_section_box_rect` asks `_heading_top` (the counterpart of `_heading_bottom`, and the
    same reason: a presentation placeholder paints its line in the *middle* of its box,
    fact 56) and sits above the painted line, falling back to below it when there is no
    room. The witness is `section_titles_do_not_print_through_the_heading`, which renames
    the sections `Section1`, `Section2`, … first: a deck whose heading contains its section
    name ("Live Demo" in a section called "Demo") otherwise has the heading's own word
    counted as the label.
88. **A text box from `createInstance` arrives filled and framed.** Measured on a freshly
    loaded deck: `FillStyle` and `LineStyle` answer `SOLID`, so a label that is not
    explicitly flattened is drawn on a grey rectangle with a line round it; both are set
    to `0` (`NONE` — the office answers these enums by *name*, fact 92). Impress is known
    to hand a new shape the attributes of the last shape created, but that could not be
    *set* from UNO in either direction — created shapes answered `SOLID` on one run and
    `NONE` on the next in one office, whichever it had been doing — so the flattening is
    not left to the default: `_draw_flat()` runs at creation **and** on every paint, so a
    box that picked a plate up (a duplicated slide, a template, an edit) is flat again
    after the next *Section Titles*. The witness is
    `section_titles_are_painted_without_a_plate`, which gives a box a solid fill and
    frame, re-runs the command and asks again — the creation-time assertion beside it is a
    bar, not a witness, for exactly that reason. A plain `com.sun.star.drawing.TextShape`
    is *not* a content placeholder — `CONTENT_SERVICES` is `OutlinerShape`/
    `SubtitleTextShape` only — and that is also what keeps a generated box out of the
    `_deck_placeholder` vote that decides what the deck looks like (fact 54); otherwise
    the second run would take its own label as the template.
89. **The look goes on the shape *before* `setString`, on its paragraphs after, and on
    each paragraph's portions after that.** The paragraph `setString` creates inherits
    from the shape, and a paragraph of a text shape may take its characters from the
    page style instead (fact 52); the portion is the third rung and the one that paints,
    so a box that was styled by hand — or duplicated from one that was — would keep its
    own size, weight and colour under a shape and a paragraph that both said something
    else. Measured once, on the neighbour of a slide that had just been duplicated, the
    paragraph enumeration answered *nothing at all* — so `_paint_section_box` asks the
    shape again after the text is in.
90. **The office's font list lives on a window peer, and asking from a second top-level
    window while a menu popup is up wedges the client.** `Toolkit` has no
    `getDeviceFontEnumeration`, a frame's container window has no `getPeer` at all
    (`AttributeError`) and `peer.createDevice()` offers no font enumeration either —
    `dev/probe_fonts.py` prints every route with what it answers. A peer of an
    `UnoControlDialog` answers `getFontDescriptors()` with **4701 descriptors = 2835
    families** (one per face, so the names have to be deduplicated). Building such a peer
    *before* the settings dialog had its own hung the client outright, although
    `dev/probe_font_peer.py` runs the same five lines with and without a document open in
    under a second: the second top-level window next to the menu's popup grab is what
    hangs. `SettingsDialog._fill_fonts` therefore reads the list from the dialog's **own**
    peer after `createPeer` and writes `StringItemList` then — words and colours still
    change after `createPeer` even though geometry does not (fact 70), measured as
    itemCount 0 → 3 with the typed value intact in `dev/probe_font_items.py`. An empty
    list is a normal outcome, not an error: the field is an editable combo either way.
91. **The dialog's peer position is not where the dialog paints.** `getPosSize()` answered
    `482x629 at 476,0` while the marker colour proved the client area is at **474,25** —
    the office reports the *frame*, so a crop taken straight from peer coordinates lands
    ~25 px high and every new label read "nothing painted". `xwininfo` answers the frame
    too (fact 76), so `dev/probe_section_fields.py` measures the offset the way
    `dev/probe_picker_ink.py` does, by painting the dialog `#7FFF00`. And a peer is not
    told when its model changes (fact 75): the plain screenshot has to be taken *before*
    the marker one, or the transparent controls keep the green behind them and every row
    of their box reads as ink.
92. **Two pyuno spellings, each worth one failed test.** `FillStyle` and `LineStyle` come
    back as an `Enum` whose `.value` is the **name** — `'NONE'`, so `int(…)` raises
    `ValueError` (`_style_is_none` accepts both spellings). And a `DrawPage` has `Width`
    and `Height` but **no `Size`** — only the shapes on it have `Size`.
93. **The position fields speak centimetres and the settings file does not.** Impress's
    own *Position and Size* dialog works in cm, which is what a user reads off it, while
    every geometry property in `core` is 1/100 mm (fact 20); `dialog.cm_to_units` and
    `units_to_cm` are the one line that joins them. Empty, rubbish and a negative number
    all mean the same thing — "where the deck's own content box is", `None` — because a
    half-typed value must not move the label to 0,0. `config.load` is the only guard
    against a hand-edited file, which is why `"1.5"`, `True`, `-4` and `-2.5` are each
    refused there (`_as_length`, `_as_point`).

94. **The first box the command can see is the template, and the settings fields are
    only what a box is drawn with when there is nothing to copy.** "Copy the position and
    formatting of the first section title textbox you see when inserting / updating
    section title" is the rule, unconditional: `apply_section_titles` looks for the first
    slide that *has* a box and is *meant* to have one, takes its rectangle and its
    characters, and paints every other box from it — including that box's own height,
    which is why the shape's `Size` is written rather than left to `TextAutoGrowHeight`.
    A box on a slide before the first section, or on a plan slide, cannot set the pattern:
    this very run deletes it, and a leftover from a re-sectioned deck must not dictate the
    deck's look (`a_stray_box_cannot_set_the_look_of_the_deck`). Where no slide has a box,
    the `section_*` settings say, and the first box written then becomes what the later
    ones copy, so one run cannot produce two different-looking labels. There is
    deliberately **no toggle** for the choice and the dialog calls the four fields
    *Default colour / font / size / X, Y, W* — a field that silently does nothing is what
    reads as "the option does not work". `report["look"]` says which of the two paths ran
    ("the first section slide's own box" or "the default settings"), because the two are
    not distinguishable from the deck alone.
95. **A user styles text on its *portion*, so a box is copied from and written to there.**
    `box.CharHeight = 28` is what a macro does and only reaches the default underneath
    everything; what the sidebar, the toolbar and `Ctrl+` change — and what the office then
    paints — is the first portion of the paragraph, which is why copying the box copied the
    *position* (geometry really does live on the shape) and lost the font, the size, the
    weight and the colour: asked at shape or paragraph level, a box the user had made 28 pt
    bold red still answered what the run that created it had written. `_look_sources`
    therefore asks portion → paragraph → shape and takes the first that answers (the
    reverse of fact 55's "ask the paragraph, the shape is only the default", which is the
    same ladder from the top: the master's sample text has no hand formatting on it, the
    user's label does), and `_paint_section_box` writes all three rungs (fact 89). The
    witness styles a box the way the editor does and asserts the copy at portion level —
    `section_titles_copy_the_first_box_the_command_sees`; `dev/debug_section_titles.py`
    prints shape, paragraph and portion side by side, which is the only way to tell "the
    copy never ran" from "the copy read the wrong level".

### Driving the office with `xdotool`

96. **A menu click left open wedges the office for every later client.** `xdotool
    mousemove X Y click 1` on the *Plan* menu takes a pointer grab, and the grab survives
    the probe that asked for it — killing such a probe half way through leaves the popup
    open and the office then answers nothing more that touches a document: the next script
    hangs in `loadComponentFromURL()` without printing a line while `pgrep`, `xdpyinfo`,
    the UNO port and `Toolkit.getFontDescriptors()` all still look healthy. It is fact 48's
    modal dialog in X clothing and fact 60's dead office without a dead process, so the
    two probes that click the menu (`dev/measure_text.py`, `dev/probe_font_menu.py`) end
    with `key Escape`, `key Escape` and a click on the canvas; when a hang is already
    there, restart the **office** — restarting the script changes nothing.

## Testing notes

`tests/run_tests.py` has no framework: `@test` collects functions, a `Skip`
exception reports "not installed" without failing, and an argument filters by
substring (`python3 tests/run_tests.py dialog`). Tests that need the installed
extension are skipped when it is not installed, so `make unit` is useful without
packaging.

The suite covers: settings round-trip and corrupt-file tolerance, where the
settings file is allowed to live, colour helpers, the point/unit conversion, the
dialog's *geometry* (every control's rectangle in the specs, and the real peer
geometry: distinct positions, non-zero sizes, nothing outside the window) plus a
control model with a native peer and read-back values and the dialog's **text**
(every control that shows words sets a `FontHeight` the size of the menu's, and
each row leaves clear air under the field above it), the inserted layout
(position of every plan slide, per-paragraph colours, the overview outside all
sections), a deck whose first slide belongs to no section, readable font sizes
with nothing drawn off the slide, the footer (copied from the deck's own slides
and rendered, frames mirrored onto a deck that carries them, and no footer
invented in a deck that has none), the template's own look
(`plan_slides_use_the_template_placeholders`: the deck's own placeholders and
their rectangles, the list clearing the painted heading, the inherited list level
with only the label replaced, the characters mirrored down to the paragraphs, the
number of a dimmed row dimmed with it; and `plan_slides_copy_the_deck_own_slides`,
where the master is left alone and the slides moved instead, so anything taken
from the master shows up as a failure), the label the rows are numbered with
(`plan_rows_are_numbered_the_way_the_template_numbers`: the deck's own counting
level with its `Suffix`, its size and its column kept; digits only where nothing
counts, then corrected to be readable; and the numerals taken from the *heading's*
level when the body draws a glyph — `list_label_follows_the_template` pins the
same rule without an office), that a named master the deck does not have means the
deck's own (`master_slide_is_used`), that a run which stops half way leaves neither
a slide nor a section boundary behind
(`insert_plan_leaves_nothing_behind_when_it_fails`, at the three places it can
stop), that removing the slides of such a wreck loses nothing of the deck,
idempotency and clean removal, the master-slide setting, `Addons.xcu` registration
read back through the configuration provider, and the `service:` URL dispatch path a
menu click takes.
The colour picker is covered the same two ways: the palette files are parsed from
disk (both namespaces, a corrupt file, a user's palette overriding a shipped one,
the recently used list sanitised on the way in and on the way out), and the
widget's geometry is checked control by control — sixty cells that do not overlap,
each cell carrying the colour and the name it stands for, the cells past the end of
the palette switched off, and every colour of a 250-colour palette reachable
through the pager. `picker_is_the_offices_dropdown` is the one that pins the *look*
the report asked for: a palette selector with the pager beside it, the palette named
once rather than repeated under the selector, a caption above each group that does
not overlap its squares or hide behind the selector, a page indicator centred between
the arrows and sized for the widest page count any palette has, the colour's name and
value under the grid with a field to type one into, one OK that Enter answers and one
Cancel flush with the grid, and `the_chooser_is_wide_enough_for_the_names_it_shows`
says no entry the dropdown can list is cut (fact 84). The "perspective-style border"
report is pinned by `colours_are_painted_flat_with_a_contrast_line`: the only controls
left that are buttons are the two real buttons, and every colour carrier is an image
control with `Border` 0, because the line is in the picture (fact 77). The picture is
checked as pixels, not as properties — `a_swatch_is_its_colour_inside_a_line_of_the_contrast_colour`
decodes the PNG `swatch.png_bytes()` writes back to a raster and asserts the inside is
the colour and the ring the contrast colour, `the_line_round_a_colour_contrasts_with_what_it_sits_on`
asserts black and white never get the same line, and
`the_chooser_tells_a_dark_theme_from_the_desktop` reads the desktop files fact 83 lists.
`every_colour_carries_a_bitmap_of_its_own` is what catches a square left unpainted: every
cell, the chip and both dialog swatches must carry a `Graphic` of their own.
Fact 85's three reports are pinned by `a_colour_is_a_square_of_pixels_and_never_a_strip`
(every colour carrier, in the constants *and* in both widgets' own specs, is `w` x
`swatch.square_units(w)`, which is the only way 22 x 12 units becomes a failure), by
`the_grid_leaves_clear_air_between_its_squares` (the pitch, and the grid's width paying
for the air) and by `colour_squares_are_square_and_apart_on_the_screen`, which asks the
peers in pixels what the specs only promise in units - a 23 x 17 cell, two neighbours
0 px apart or a hex field too narrow for `#1F4E79` each fail it;
`the_hex_field_is_wide_enough_for_the_value_it_shows` is the same bar without an
office.
`picker_paints_nothing_on_top_of_anything_else` compares every pair of painted
controls, which is the only way a cramped line becomes an assertion, and
`clicking_a_square_answers_the_picker` fires the listeners that were really attached
to the peers — a label answers nothing until a `mouseReleased` handler exists
(fact 79).

The message box is covered the same two ways too: `message_box_reports_what_it_says`
checks the wrapped text (a log path is one long word and has to reach the box), the
controls inside the window, the buttons in the bottom right and exactly one
`DefaultButton`, on the primary; `message_box_answers_its_buttons` builds the box
without the modal loop and checks what each button and each key answers, against a
real window. `toggling_the_debug_log_says_what_it_did` is the user's report: the
marker flips *and* a box naming the log file is asked for — comment the

nothing at all".

Things that are easy to break and are covered: re-running `insert_plan` must
yield the identical slide list (this is what caught the section-corruption bug),
and `remove_plan` must return to the original seven slides and be harmless when

page and therefore hides that spelling; it builds its own deck, saves it, reads
it back and asserts the section ranges (`indexes`), their `Id`s and that the
trailing unsectioned slide ends up in the last section.

The section-name box is covered on both sides as well. In the document:
`section_titles_name_every_section_slide` (one box per section slide, saying its own

`section_titles_are_not_drawn_on_the_plan_slides`, `remove_section_titles_loses_nothing_of_the_deck`,
`section_titles_copy_the_first_box_the_command_sees` (fact 94's rule and fact 95's level:
the box is styled the way the *editor* styles text — on its portion — and every other box

`a_stray_box_cannot_set_the_look_of_the_deck` (the box being deleted by this run is not

*drawn as* is checked on the rendered page: `section_titles_do_not_print_through_the_heading`

### Looking at the result

Whether the office has an API at all is worth asking before writing a widget
against it: `dev/probe_api.py` searches the type repository by hierarchical name
and `dev/probe_palettes.py` reports where the palettes and the deck's own colours
actually come from; both are what the picker's design rests on.

For the two widgets the office's own versions are the specification, and both have a
probe that photographs them: `dev/probe_picker_look.py` opens the chooser the way the
settings dialog does (open, palette switched, second page, pointer on a square) and
`dev/probe_message_box.py` puts our box next to every spelling of
`createMessageBox` there is, printing what each answered. `dev/probe_picker_peers.py`
prints every control's rectangle in model units and in peer pixels and then measures
the *ink* of the pager row — it finds the client area by the known colour of a
square painted `#7FFF00`, because the window's peer answers `0,0` (fact 76) and the
desktop here is the same grey as the dialog — and prints how far off centre the page
indicator's glyphs actually are. When a layout looks wrong, that table says whether
the layout or the reading of it is at fault.
`dev/probe_swatch_look.py` is the same trick for a colour: it puts one candidate
control per row (a button, an image control and a label, each with every border style
and with and without a border colour), finds each square in the screenshot *by its
colour*, and prints the ring of pixels around it — a bevel is dark on two sides and
light on the other two, a solid line is one colour all round — plus which border
properties the model has at all and whether a click reaches it. `dev/probe_underline.py`
photographs six spellings of one line to find out what draws a mnemonic stroke.
`dev/probe_border_colour.py` lays one colour out under every `Border` value with and
without a `BorderColor` and prints the ring it finds: all six non-zero styles answer the
theme's `#2B2E39` and 0 of 180 ring pixels red (fact 78). `dev/probe_swatch_ring.py`, with
the `2` and `3` follow-ups that add the window's own position to the pointer coordinates
(fact 79), photographs a candidate's ring and tells a bevel from a solid line, and
`dev/probe_swatch_stream.py` checks the raw picture — it unzips the PNG and confirms the
`Graphic` the office hands back really carries the bytes that were written.
`dev/probe_theme.py` prints every route to the theme next to what each one answers, which
is how fact 83's dead ends were ruled out. `dev/probe_swatch_bitmap.py` puts the three
candidate controls on screen with a bitmap and prints which model properties each has, and
`dev/probe_picker_width.py` renders the palette dropdown at nine widths, and
`dev/probe_selector_fit.py` renders every palette name twice - in a `FixedText` nothing
can cut and in a dropdown at the width in question - which is where fact 84's per-glyph
and chrome constants come from. `dev/probe_picker_ink.py` photographs the chooser's
whole header and grid and answers the four pixel reports at once: the name against the
same name in a reference label, the ink of `<`, the page number and `>` and the air
between the *glyphs*, each colour square's control box, its block of colour and its
ring, and the value typed into the hex field at four widths until the ink stops growing
(facts 84 and 85). `dev/probe_debug_toggle.py` drives the menu item itself through the installed
extension, which is how "does nothing" was shown to be an empty box rather than a Job
that never ran.

The section-name box has three of its own. `dev/debug_section_titles.py` prints what the
office really says about the boxes: every slide's section, each box's name (this is where
a duplicated slide's `PlanImpress:SectionText:Slide: 1` was seen, fact 86), its rectangle
and its characters at shape, paragraph *and* portion level — the third column is what
paints, and it is how "the position copies but the font does not" was told from a copy that
never ran (fact 95). `dev/render_section_titles.py` inserts
the labels, exports a PDF and prints the bands of glyphs `pdftotext -bbox` answers with —
the only witness for "the label does not print through the heading" (fact 87).
`dev/probe_section_fields.py` photographs the settings dialog and prints, per control of
the new rows, how many rows of ink it holds and how tall the tallest is, so a label that
paints nothing, a font dropdown with no names and a caption drawn behind its neighbour are
each visible; it anchors the crops on the dialog painted `#7FFF00` because the peer reports
the frame, not the client area (fact 91). What the font list can and cannot be asked of is
`dev/probe_fonts.py` (every route to the office's fonts with what each answers) and
`dev/probe_font_peer.py` (the five steps of `installed_fonts` timed, 4701 descriptors in
0.1 s with or without a document) — the hang those were chasing is *when* a second
top-level peer is created, which `dev/probe_font_menu.py` isolates by opening the *Plan*
menu first, and the fix is measured by `dev/probe_font_items.py` (itemCount 0 → 3 with the
typed value intact, fact 90).

Assertions cannot tell you a slide looks right, and a font size that is wrong by
a factor of ten passed every test once. To see the generated deck: export a
document with the plan slides inserted to PDF
(`storeToURL(..., FilterName=impress_pdf_Export)`) and rasterise it with
`pdftoppm`/`montage`, then look at the images. `dev/debug_sizes.py` prints the
`CharHeight` at shape/paragraph/portion level plus the rectangles, which is
usually the faster way to spot a layout problem.

For anything the *text* of a slide has to prove — the footer above all — the PDF
is the only witness: `pdftotext -f N -l N deck.pdf -` per page is what
`tests/run_tests.py::_pdf_page_texts` and `dev/debug_footer_saved.py` assert on,
because `getString()` of a field reports the stored placeholder rather than what
is drawn (fact 41). `dev/debug_footer_render.py` exports several candidate recipes
as one document so they can be compared as images, which is how the footer
mechanism was picked.

## If something is broken

1. Is the extension registered?
   `unopkg -env:UserInstallation=file://$PWD/loprofile list` — look for
   `is registered: yes` under each bundled package.
2. Does the office still have the old code? Restart (`make install`).
3. Read `loprofile/user/planimpress/error.log` and `out/soffice.log`.
4. Turn on the debug log and reproduce.
5. Reproduce in isolation with one of the `dev/debug_*.py` / `dev/dep_probe.py`
   scripts before changing `src/` — every surprising behaviour in this project
   was nailed down that way, and the answer usually is one of the numbered facts
   above.
